장바구니에 상품을 담는 기능에는 서로 다른 판단이 섞여 있습니다. 기존 상품과 같은 매장인지 확인하고, 다른 매장이라면 교체 여부를 물은 뒤, 사용자의 선택에 따라 장바구니를 변경합니다. 모두 장바구니와 관련된 코드지만, 매장을 비교하는 조건과 확인창을 띄우는 절차는 변경되는 이유가 다릅니다. 확인 화면을 바꾸더라도 한 매장만 담을 수 있다는 조건은 유지됩니다.

FSD(Feature-Sliced Design)에서 엔티티와 피처를 나누는 기준도 여기서 찾을 수 있습니다. **엔티티에는 업무 개체의 규칙과 상태를, 피처에는 그 규칙을 사용해 사용자의 요청을 처리하는 흐름을 둡니다.** 주문 앱의 담기와 결제를 예로, 이 구분이 코드와 의존성에 어떻게 반영되는지 살펴보겠습니다. 한 화면에서만 사용하는 흐름을 페이지에 두는 경우도 함께 다룹니다.

## 장바구니 규칙과 상품 담기 절차

장바구니에 A 매장 상품이 담긴 상태에서 B 매장의 상품을 선택하면 교체 여부를 확인해야 합니다. 이 주문 앱에서는 두 매장의 상품을 함께 주문할 수 없기 때문입니다. 사용자가 취소하면 장바구니를 유지하고, 승인하면 B 매장의 상품으로 교체합니다.

이 동작을 한 함수에 작성하면 매장 비교, 확인창, 장바구니 변경이 모두 붙어 있습니다. 하지만 메뉴판에서 담든 메뉴 상세에서 담든 같은 매장끼리만 담을 수 있다는 조건은 같습니다. 반면 교체 여부를 모달로 물을지, 별도 화면에서 받을지는 담기 기능을 어떻게 제공하느냐에 따라 달라집니다.

그래서 매장을 비교하는 조건은 장바구니 엔티티에 두고, 확인을 받은 뒤 교체하는 순서는 담기 피처에 둡니다. 아래 코드에서 엔티티는 교체가 필요한지만 반환합니다.

```ts
// entities/cart/model/cart.ts
export type Cart = {
  storeId: string | null;
  lines: Array<{ menuId: string; quantity: number }>;
};

export function needsStoreReplacement(cart: Cart, nextStoreId: string) {
  // 비어 있다면 기존 상품을 지울 필요가 없습니다.
  return cart.lines.length > 0 && cart.storeId !== nextStoreId;
}
```

담기 피처는 이 결과를 사용해 사용자에게 확인을 받고 장바구니를 변경합니다. 여기서는 확인 UI와 상태 변경 함수를 인자로 받아 연결했습니다.

```ts
// features/add-to-cart/model/addToCart.ts
import { needsStoreReplacement, type Cart } from '@/entities/cart';

type AddInput = { storeId: string; menuId: string; quantity: number };
type Dependencies = {
  confirmReplacement: () => Promise<boolean>;
  replaceCart: (input: AddInput) => void;
  appendItem: (input: AddInput) => void;
};

export async function addToCart(
  cart: Cart,
  input: AddInput,
  deps: Dependencies,
) {
  if (needsStoreReplacement(cart, input.storeId)) {
    // 기존 상품을 잃지 않도록 사용자가 승인한 뒤 교체합니다.
    if (!(await deps.confirmReplacement())) return;
    deps.replaceCart(input);
    return;
  }
  deps.appendItem(input);
}
```

교체 확인을 모달에서 별도 화면으로 바꾼다면 `confirmReplacement`의 구현이 바뀝니다. 한 매장만 담을 수 있다는 조건은 그대로이므로 `needsStoreReplacement`를 수정할 필요는 없습니다. 반대로 여러 매장의 상품을 함께 담을 수 있게 된다면 장바구니 모델과 조건을 바꾸고, 담기 절차에서도 교체 확인이 필요한지 다시 살펴봐야 합니다. 규칙을 분리한다고 변경이 항상 한 파일에서 끝나는 것은 아니지만, 무엇이 바뀌었는지에 따라 살펴볼 코드는 구분할 수 있습니다.

[공식 문서](https://feature-sliced.design/docs/reference/layers)는 엔티티를 서비스가 다루는 업무 개념으로, 피처를 사용자의 주요 상호작용으로 설명합니다. 담기 예제에서 엔티티는 “장바구니에 무엇을 담을 수 있는가”를 판단하고, 피처는 “사용자가 선택한 상품을 어떻게 담을 것인가”를 처리합니다. 엔티티에는 데이터와 규칙뿐 아니라 API 함수나 재사용할 UI도 들어갈 수 있습니다. 따라서 “규칙은 엔티티”라는 표현은 조건 검사 코드를 배치하는 기준이며, 엔티티에 순수 함수만 둘 수 있다는 의미는 아닙니다.

## 담기와 결제가 공유하는 장바구니 상태

장바구니 상태는 담기부터 결제 완료까지 여러 기능에서 사용합니다. 기존 구현에서는 이 상태를 보관하는 스토어가 장바구니 피처 안에 있었습니다. 메뉴판에서는 상품을 담고, 장바구니 화면에서는 수량을 바꾸고, 결제 결과를 처리하는 쪽에서는 결제가 끝난 장바구니를 비워야 했습니다.

상태가 한 피처 안에 있으니 다른 피처들이 그 상태를 사용하려고 장바구니 피처를 참조했습니다. 장바구니 피처도 결제 피처를 사용하면서 두 피처가 서로를 import하는 관계가 생겼습니다. 그 결과 담기 기능도 장바구니 피처를 통해 결제 코드에 의존하게 됐습니다.

장바구니 상태와 갱신 함수를 `entities/cart`로 옮기자 담기와 결제 코드가 각각 장바구니를 사용할 수 있게 됐습니다. 상품을 추가하거나 결제 후 비우는 시점은 각 기능이 정하지만, 두 기능이 읽고 변경하는 상품과 수량은 같은 장바구니 데이터입니다. 이를 엔티티에서 관리하면 한 피처가 다른 피처의 내부 스토어를 가져다 쓸 필요가 없습니다.

아래는 이 분리를 적용하고, 결제 절차는 장바구니 페이지에 둔 구성입니다. `features/add-to-cart/model`은 장바구니 조건을 확인하고 상품을 담으며, `pages/cart/model`은 주문을 생성하고 결제가 완료되면 장바구니를 비웁니다. 두 코드가 같은 `entities/cart/model`을 사용합니다.

> `entities/cart/model`에서 `entities`는 역할과 의존 방향을 구분하는 **레이어**(layer), `cart`는 장바구니 관련 코드를 묶은 **슬라이스**(slice), `model`은 그 안에서 상태와 규칙을 담당하는 **세그먼트**(segment)입니다.

그래프의 외부 참조는 각 슬라이스의 **공개 API**(public API)를 거칩니다. 공개 API는 다른 슬라이스에서 사용할 함수나 타입을 내보내는 진입점으로, 여기서 API는 서버 통신만을 뜻하지 않습니다. 예를 들어 장바구니는 `index.ts`에서 필요한 항목을 내보내고, 담기 피처는 내부 파일의 위치를 몰라도 이를 사용할 수 있습니다.

```ts
// entities/cart/index.ts
export { needsStoreReplacement } from './model/cart';
export type { Cart } from './model/cart';
```

장바구니를 비우는 함수와 ‘언제 비울지’를 정하는 코드도 구분합니다. 상태를 초기화하는 함수는 엔티티에 두지만, 결제 완료를 확인한 뒤 호출하는 순서는 결제 코드에 남깁니다. 장바구니가 결제 화면의 진행 순서까지 알아야 할 이유는 없습니다.

이처럼 여러 기능이 같은 업무 데이터를 생성·수정·삭제한다면, 상태를 특정 피처에 두었을 때 불필요한 참조가 생기는지 확인할 수 있습니다. 여러 곳에서 읽는 값이라는 이유만으로 모두 엔티티로 옮기는 것은 아닙니다. 모달 열림 여부처럼 특정 화면을 사용하는 동안만 필요한 값은 그 UI나 페이지에서 관리할 수 있습니다.

## 사용자 흐름이라고 모두 피처로 만들지는 않습니다

앞의 담기 예제는 메뉴판과 메뉴 상세에서 같은 절차를 사용하므로 피처에 두었습니다. 결제를 시작하는 화면이 장바구니 하나뿐이라면, 결제라는 사용자 흐름이 있다는 이유만으로 `features/checkout`을 따로 만들 필요는 없습니다.

[FSD v2.1 문서](https://feature-sliced.design/docs/guides/migration/from-v2-0)는 **Pages First**를 권장합니다. 화면을 페이지 단위로 구성하고, UI와 로직을 우선 그 페이지에 둔 뒤 여러 페이지에서 재사용할 필요가 생기면 하위 레이어로 옮기는 접근입니다. 페이지는 관련 코드를 찾을 때 익숙한 단위이므로, 한 화면에서만 쓰는 코드까지 미리 흩어 놓지 않아도 됩니다.

이 기준으로 보면 장바구니 화면과 전용 결제 절차는 같은 페이지 안에 둘 수 있습니다. 페이지에 둔다는 것이 하나의 컴포넌트에 모두 작성한다는 뜻은 아닙니다. 화면은 `ui`, 결제 절차는 `model/checkout`으로 나누면 됩니다.

```text
pages/cart/
  ui/CartPage.tsx
  model/checkout/
    buildOrderRequest.ts
    useCheckout.ts
  index.ts
```

기존 장바구니 화면처럼 피처에 화면과 전용 훅이 들어 있다면, 둘을 함께 페이지로 옮기는 구성을 고려할 수 있습니다. 외부에는 페이지 컴포넌트만 공개하고 결제 훅은 페이지 내부에서 사용합니다. 화면만 옮긴 채 내부 훅을 피처의 공개 API로 모두 내보낼 필요는 없습니다. 이후 다른 화면에서도 같은 검증·주문 요청·완료 처리가 필요해지면 그때 `features/checkout`으로 분리할 수 있습니다.

담기와 결제는 모두 사용자 흐름이지만, 재사용 범위에 따라 위치가 달라집니다. 규칙과 절차를 구분하는 일과, 그 절차를 별도 피처로 추출하는 일은 나눠서 판단해야 합니다.

## 화면에서 엔티티로 향하는 의존성

담기와 결제를 나눈 방식을 주문 앱 전체로 넓히면, 화면은 필요한 기능과 데이터를 가져와 사용하고 엔티티는 자신을 사용하는 화면을 참조하지 않는 구성이 됩니다. 메뉴판은 담기 버튼과 메뉴 조회를, 장바구니 화면은 결제 절차와 장바구니 상태를, 주문 확인 화면은 주문 조회를 사용합니다.

FSD의 [레이어 import 규칙](https://feature-sliced.design/docs/reference/layers#import-rule-on-layers)은 이 방향을 정해 둡니다. 다른 슬라이스를 import할 때는 자신의 레이어보다 아래에 있는 코드만 사용할 수 있습니다. 레이어의 순서는 `app → pages → widgets → features → entities → shared`이며, 같은 슬라이스 안에서는 `ui`에서 `model`을 사용하는 것처럼 연결할 수 있습니다.

아래 그래프에서 메뉴 탐색·담기, 결제, 주문 확인을 선택하면 각각이 사용하는 세그먼트와 import 방향을 볼 수 있습니다. `app`은 화면 라우팅을 연결하고, `shared`는 공통 버튼과 HTTP 클라이언트를 제공합니다. 여러 화면에서 재사용할 큰 UI 블록이 필요하면 `widgets`에 둘 수 있지만, 모든 레이어를 반드시 만들어야 하는 것은 아닙니다.

장바구니 모델이 결제 화면을 import하면, 장바구니를 사용하는 메뉴판도 결제 화면의 코드에 의존하게 됩니다. 화면이 모델을 가져다 쓰는 방향으로 연결해야 장바구니를 다른 화면에서도 사용할 수 있고, 확인창이나 라우팅을 바꿀 때 모델까지 함께 수정하지 않아도 됩니다.

메뉴판에서 장바구니로, 장바구니에서 주문 확인으로 이동하는 순서는 import 방향과 다릅니다. 화면 이동은 라우팅으로 연결하며 페이지끼리 서로를 import할 필요는 없습니다. 장바구니 페이지가 피처를 거치지 않고 엔티티를 직접 사용하는 것도 가능합니다.

같은 레이어의 서로 다른 슬라이스를 import하는 것은 **교차 참조**(cross-import)라고 합니다. 앞에서 장바구니 피처와 결제 피처가 서로를 사용했던 구조가 여기에 해당합니다. [공식 가이드](https://feature-sliced.design/docs/guides/issues/cross-imports)는 공통 로직을 하위로 옮기거나, 상위에서 두 기능을 연결하거나, 항상 함께 바뀌는 슬라이스를 합치는 방법을 제안합니다. 장바구니 상태를 엔티티로 옮기거나, 여러 피처를 사용하는 화면을 페이지에 두는 구성이 이에 해당합니다.

기존 구현에서 메뉴판이 장바구니 금액 계산을 사용하는 부분에는 피처 간 참조가 남아 있었습니다. 이 참조는 `index.ts`에서 공개한 항목만 한 방향으로 사용하도록 제한했습니다. 공개 API를 거쳐도 같은 레이어의 의존은 남습니다. 이 참조를 더 줄이려면 계산이 장바구니 자체의 규칙인지, 여러 개체를 사용하는 절차인지 다시 살펴볼 필요가 있습니다.

## 메뉴·장바구니·주문을 나누는 기준

엔티티를 나눌 때는 데이터가 독립적으로 조회·변경되는지 살펴볼 수 있습니다. 이 주문 앱의 메뉴 옵션과 재고는 메뉴 없이 따로 조회하거나 변경하지 않았고, 같은 API 응답으로 전달됐습니다. 이를 각각의 슬라이스로 나누면 메뉴 하나를 다루기 위해 여러 엔티티가 서로를 참조해야 했습니다. 그래서 옵션과 재고는 메뉴 안에 두었습니다.

장바구니와 주문은 별도로 관리했습니다. 장바구니는 결제 전에 사용자가 상품과 수량을 수정하지만, 생성된 주문은 서버와 매장이 진행 상태를 바꿉니다. 상품을 담기만 하고 떠나면 주문은 생기지 않고, 주문이 생성된 뒤 장바구니를 비워도 주문 기록은 남아야 합니다. 둘은 생성되고 변경되고 사라지는 시점이 다릅니다.

가격을 다루는 방식에서도 차이가 드러납니다. 이 프로젝트의 장바구니에는 상품과 옵션의 식별자, 수량을 보관하고 표시 금액을 다시 계산하도록 했습니다. 수령방법을 바꾸거나 로그인하거나 메뉴 가격이 바뀌면 적용할 금액도 달라지기 때문입니다. 결제 직전에는 서버에서 가격과 할인을 검증해 청구 금액을 확정해야 합니다.

생성된 주문에는 주문 당시의 가격과 상품 정보가 필요합니다. 장바구니처럼 최신 메뉴 가격으로 다시 계산하면 나중에 주문 내역을 열었을 때 결제한 금액과 다른 값이 보일 수 있습니다. 장바구니와 주문을 분리하면 최신 가격으로 계산할 데이터와 결제 당시의 값을 유지할 데이터를 각각 관리할 수 있습니다.

반대로 여러 개체를 함께 사용한다고 해서 그 코드를 새 엔티티로 만들지는 않습니다. 기존 코드에는 장바구니와 메뉴 데이터를 가져와 주문 요청을 만드는 매퍼가 주문 엔티티 안에 있었습니다. 사용하는 곳이 결제 절차 하나라면, 이 매퍼는 결제 코드가 있는 `pages/cart/model/checkout`으로 옮길 수 있습니다. 주문 API 응답을 주문 모델로 바꾸는 함수는 주문 엔티티에 둘 수 있지만, 결제를 위해 여러 개체의 데이터를 조합하는 함수는 그 절차와 함께 두면 요청 구성과 호출 순서를 한곳에서 확인할 수 있습니다.

이때 함수가 순수 함수인지는 위치를 결정하는 기준이 아닙니다. 외부 상태를 바꾸지 않고 입력에 따라 결과만 반환하는 함수라도, 결제 요청에 어떤 인증 정보를 넣을지 고르는 판단이라면 결제 코드에 속할 수 있습니다. 매장 비교를 엔티티에 둔 이유도 순수 함수여서가 아니라 장바구니에 담을 수 있는 조건을 검사하기 때문입니다.

## 규칙, 흐름, 사용 범위

장바구니 예제에서 엔티티는 담을 수 있는 조건과 상품 상태를 제공하고, 담기와 결제 코드는 이를 사용해 각각의 절차를 수행합니다. 같은 규칙을 여러 기능에서 사용하면서도, 확인 UI나 결제 순서는 각 기능에서 변경할 수 있는 구조입니다.

“규칙은 엔티티, 흐름은 피처”는 이 역할을 구분하는 기준입니다. 여기에 사용 범위를 더하면 실제 배치가 정해집니다. 메뉴판과 메뉴 상세가 공유하는 담기는 피처에, 장바구니 화면에서만 실행하는 결제는 페이지에 둡니다. 장바구니 상태는 두 절차가 함께 사용하는 엔티티에 남습니다.
