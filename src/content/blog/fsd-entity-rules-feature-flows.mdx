FSD에서 코드의 위치를 정할 때는 **개체가 지켜야 할 규칙**, **사용자가 수행하는 흐름**, **화면의 조립**을 구분합니다. 주문 앱이라면 한 매장만 담는 조건은 장바구니의 규칙이고, 다른 매장 상품을 담기 전에 교체 여부를 묻는 절차는 사용자 흐름입니다.

“규칙은 엔티티, 흐름은 피처”는 이 경계를 판단하기 위한 제 해석입니다. 공식 정의를 대체하는 문장은 아니며, 한 화면에서만 쓰는 흐름은 페이지에 둘 수 있습니다. 아래에서는 공식 문서의 기준과 주문 예시를 연결해 코드 배치, 상태 소유권, import 경계를 정리합니다.

## 코드 배치 기준

| 코드의 책임과 사용 범위                | 기본 위치  | 주문 앱의 예                           |
| -------------------------------------- | ---------- | -------------------------------------- |
| 앱 전체의 초기화와 연결                | `app`      | 라우터, 프로바이더                     |
| 한 화면의 UI와 전용 로직               | `pages`    | 장바구니 화면, 해당 화면의 결제 절차   |
| 재사용하는 독립적인 큰 UI 블록         | `widgets`  | 여러 화면의 공통 매장 헤더             |
| 여러 화면에서 사용하는 사용자 상호작용 | `features` | 메뉴판·메뉴 상세의 담기, 수령방법 변경 |
| 재사용할 업무 개체의 상태와 규칙       | `entities` | 장바구니 상태, 메뉴의 옵션 선택 조건   |
| 업무 규칙을 포함하지 않는 기반 기능    | `shared`   | HTTP 클라이언트, 버튼, 날짜 도구       |

[FSD v2.1의 Pages First](https://feature-sliced.design/docs/guides/migration/from-v2-0)에 따라 새 UI와 로직은 우선 해당 페이지에 둡니다. 여러 페이지에서 같은 책임을 공유할 때 하위 레이어로 추출하며, 파일이 길어졌다는 이유만으로 피처를 만들지는 않습니다. 같은 페이지 안에서도 `ui`, `model`, `api`로 역할을 나눌 수 있습니다.

예를 들어 결제를 시작하는 화면이 장바구니 하나라면 `pages/cart/model/checkout`에 절차를 둡니다. 다른 화면에서도 동일한 검증·요청·완료 처리가 필요해지면 `features/checkout`을 검토합니다. 버튼 이름이 같다는 사실보다 실제로 공유하는 절차가 있는지가 기준입니다.

## 레이어와 import 방향

> **레이어·슬라이스·세그먼트란?**
> 레이어는 책임과 의존 범위를 나누고, 슬라이스는 업무상 관련된 코드를 묶으며, 세그먼트는 그 안의 UI·모델·통신 같은 역할을 구분합니다.

[Layers](https://feature-sliced.design/docs/reference/layers)의 기본 규칙은 다른 슬라이스를 참조할 때 더 아래 레이어만 import하도록 하는 것입니다. 같은 슬라이스 내부 참조는 가능하며, 슬라이스를 두지 않는 `app`과 `shared`는 별도로 취급합니다. 사용하지 않는 레이어까지 모두 만들 필요는 없습니다.

주문 앱의 참조 관계를 세그먼트 단위로 펼치면 다음과 같습니다. 각 노드에는 소속 레이어·슬라이스, 세그먼트, 대표 코드를 표시했습니다. 페이지의 `ui`가 피처의 `ui`와 자체 `model`을 사용하고, 사용자 흐름이 엔티티의 `model`·`api`를 참조하는 관계를 따라볼 수 있습니다.

<FsdOrderMap />

주문 절차는 메뉴판에서 장바구니를 거쳐 주문 확인으로 이어지지만, 그 순서대로 페이지끼리 import하지는 않습니다. 각 페이지가 필요한 하위 코드를 참조하고, 화면 이동은 라우팅으로 연결합니다. `pages/cart`가 `features`를 거치지 않고 `entities/cart`를 직접 사용하는 것도 가능합니다.

하위 모델이 상위 화면을 참조하지 않으면 장바구니의 조건을 이해하기 위해 결제 화면의 내부까지 읽을 필요가 없습니다. 공통 모델을 변경할 때는 이를 사용하는 상위 코드를 확인합니다. import 방향은 책임의 경계를 정하고, 변경 시 확인할 소비자를 추적하는 기준이 됩니다.

## 엔티티와 사용자 흐름의 경계

### 개체의 조건과 사용자 반응 분리

[공식 엔티티 설명](https://feature-sliced.design/docs/reference/layers#entities)은 업무 개념을 중심으로 데이터 저장, 검증 스키마, API 함수, 재사용할 화면 표현을 함께 둘 수 있다고 설명합니다. 따라서 “엔티티는 규칙”이라고 해서 순수 함수만 남기거나 UI와 API를 모두 피처로 보내려는 것은 아닙니다. 배치할 때는 그 코드가 장바구니 자체를 설명하는지, 특정 사용자 절차를 설명하는지 판단합니다.

이 주문 앱의 장바구니는 한 번에 한 매장의 상품만 담습니다. 다른 매장의 메뉴를 선택했을 때 현재 장바구니와 함께 담을 수 있는지는 장바구니의 조건입니다. 기존 상품을 지울지 묻고 사용자가 승인하면 교체하는 절차는 담기 흐름이 맡습니다.

다음 코드는 그 경계를 설명하기 위한 예제입니다. 엔티티는 판단 결과를 반환하고, 상위 흐름이 확인 UI와 상태 변경을 연결합니다.

```ts
// entities/cart/model/cart.ts
export type Cart = {
  storeId: string | null;
  lines: Array<{ menuId: string; quantity: number }>;
};

export function needsStoreReplacement(cart: Cart, nextStoreId: string) {
  // 빈 장바구니는 기존 매장을 교체할 필요가 없습니다.
  return cart.lines.length > 0 && cart.storeId !== nextStoreId;
}
```

```ts
// features/add-to-cart/model/addToCart.ts
import { needsStoreReplacement, type Cart } from '@/entities/cart';

type AddInput = { storeId: string; menuId: string; quantity: number };
type Dependencies = {
  confirmReplacement: () => Promise<boolean>;
  replaceCart: (input: AddInput) => void;
  appendItem: (input: AddInput) => void;
};

export async function addToCart(
  cart: Cart,
  input: AddInput,
  deps: Dependencies,
) {
  if (needsStoreReplacement(cart, input.storeId)) {
    // 규칙 위반 시 어떤 선택을 제공할지는 사용자 흐름이 결정합니다.
    if (!(await deps.confirmReplacement())) return;
    deps.replaceCart(input);
    return;
  }
  deps.appendItem(input);
}
```

메뉴판과 메뉴 상세에서 이 담기 절차를 함께 쓴다면 `features/add-to-cart`가 재사용 경계가 됩니다. 한 페이지 안에서만 사용한다면 같은 함수를 그 페이지의 `model`에 둘 수 있습니다. 확인창을 토스트나 별도 화면으로 바꾸더라도 한 매장만 담는 조건은 유지되므로, 두 책임을 분리한 이유가 드러납니다.

### 함수의 형태보다 책임으로 판단

결제 요청에 어떤 인증 정보를 넣을지 고르는 함수도 입력과 출력만 있는 순수 함수로 작성할 수 있습니다. 그렇더라도 결제 절차에서만 의미가 있다면 그 흐름이 소유하는 편이 맞습니다. 순수성은 실행 방식에 관한 성질이고, FSD에서의 위치는 코드의 책임과 사용 범위에 관한 판단입니다.

주문 앱의 규칙과 반응을 나란히 두면 다음과 같이 구분할 수 있습니다.

| 개체의 조건                                        | 그 조건을 사용하는 흐름                               |
| -------------------------------------------------- | ----------------------------------------------------- |
| 장바구니에는 한 매장의 상품만 담습니다             | 다른 매장 상품을 담기 전에 교체 여부를 묻습니다       |
| 메뉴의 재고는 무제한·품절·잔여 수량으로 구분됩니다 | 결제 전 최신 재고를 확인하고 변경된 상품을 안내합니다 |
| 포장 주문에는 컵 선택이 필요합니다                 | 수령방법을 바꿀 때 컵이 없는 항목의 선택을 요청합니다 |
| 주문에는 허용된 상태 전이가 있습니다               | 결제 후 서버에서 주문을 조회해 결과 화면을 결정합니다 |

여러 엔티티의 조건을 함께 적용해야 한다면 조합하는 코드는 상위에 둡니다. 컵 선택 규칙 자체와, 수령방법 변경 도중 어떤 항목을 먼저 보여 줄지는 다른 책임입니다. 결제 완료 여부 역시 클라이언트의 화면 전환이나 콜백만으로 확정하지 않고 서버의 주문·결제 상태를 확인해야 합니다.

### 가격 계산과 확정 금액 구분

이 프로젝트의 장바구니는 상품과 옵션의 식별자, 수량을 보관하고 화면에서 금액을 계산하는 방식입니다. 수령방법, 회원 자격, 최신 메뉴 가격에 따라 표시 금액이 달라지므로, 담을 때 계산한 금액을 계속 재사용하지 않으려는 선택입니다. 이는 모든 장바구니에 적용할 FSD 규칙은 아닙니다. 가격을 일정 시간 보장하는 서비스라면 견적 식별자와 만료 시각을 보관하는 설계가 필요할 수 있습니다.

이 방식에서도 결제 직전에는 서버에서 가격과 할인 적용 결과를 검증해야 합니다. 화면의 계산은 예상 금액을 보여 주는 역할이며, 실제 청구 금액의 확정과 구분합니다. 주문이 생성된 뒤에는 당시의 가격과 상품 정보가 필요하므로, 주문까지 장바구니와 같은 방식으로 최신 메뉴 가격을 따라가게 만들지는 않습니다.

## 상태 소유권과 교차 참조

여러 흐름이 같은 업무 상태를 사용한다면 특정 피처의 내부 상태로 두지 않습니다. 장바구니 상태를 장바구니 피처가 소유하면, 메뉴판의 담기와 결제 완료 후 초기화가 그 피처를 참조하게 됩니다. 장바구니 피처가 결제 피처까지 사용하면 양방향 의존으로 이어집니다.

장바구니 상태와 갱신 함수를 `entities/cart`로 분리하면 각 흐름이 필요한 API를 직접 사용할 수 있습니다. 아래 그림은 장바구니 화면의 `ui`·`model`, 담기 피처의 `ui`·`model`, 엔티티의 `model`·`api`가 어떤 코드에 의존하는지 보여 줍니다. 외부 슬라이스의 세그먼트로 이어지는 화살표는 내부 경로의 직접 import가 아니라, 해당 슬라이스의 공개 API를 통해 제공받는 코드를 나타냅니다.

<FsdCartDependencies />

상태를 내린 뒤에는 담기와 결제 완료 처리가 각각 장바구니의 공개 API를 사용할 수 있습니다. 한 화면에서만 실행하는 결제 흐름은 `pages/cart`에 남겨도 같은 방식으로 연결됩니다. 상태를 함께 읽는다는 이유로 사용자 절차까지 엔티티로 옮기지는 않습니다.

상태를 추가하는 흐름과 비우는 흐름이 다르면 소유권을 점검합니다. 여러 곳에서 사용하는 값이라고 모두 엔티티로 옮기지는 않습니다. 모달 열림 상태나 검색 입력처럼 특정 화면의 수명에 묶인 값은 상위 페이지나 해당 UI가 소유할 수 있으므로, 먼저 그 상태가 어떤 개체를 나타내는지 확인합니다.

### 같은 레이어의 슬라이스를 참조할 때

[Cross-import 가이드](https://feature-sliced.design/docs/guides/issues/cross-imports)는 같은 레이어의 슬라이스 간 의존을 결합의 신호로 보고, 합치기·공통 도메인 로직 내리기·상위에서 조립하기를 제안합니다. 이를 적용하기 어렵고 참조가 불가피하면 공개 API로 범위를 제한하는 전략도 설명합니다. 기본 import 규칙과 이 타협을 구분해서 읽어야 합니다.

교차 참조가 생기면 다음 순서로 정리합니다.

1. 항상 함께 바뀌는 슬라이스라면 하나로 합칩니다.
2. 여러 흐름이 공유하는 개체의 규칙과 상태는 엔티티로 분리합니다.
3. 서로 다른 피처의 UI나 동작을 연결하는 코드는 페이지 등 상위 레이어에서 조립합니다.
4. 참조를 유지해야 한다면 공개 API로 범위를 제한하고, 이유와 재검토 조건을 기록합니다.

메뉴판과 장바구니 화면이 같은 금액 계산을 사용한다면, 먼저 계산의 책임을 확인합니다. 장바구니 자체의 규칙이면 엔티티에 두고, 메뉴 가격·회원 자격·수령방법을 조합하는 계산이면 필요한 엔티티를 사용하는 상위 코드에서 연결합니다. 다른 피처의 `index.ts`를 거치더라도 같은 레이어의 의존성이 사라지는 것은 아닙니다.

엔티티끼리도 실제 데이터 관계 때문에 참조가 필요할 수 있습니다. [Public API의 `@x` 표기](https://feature-sliced.design/docs/reference/public-api#public-api-for-cross-imports)는 `entities/menu/@x/order.ts`처럼 특정 소비자에게만 제공하는 경계를 명시합니다. 참조를 숨기지 않는 방법이지 임의의 엔티티를 연결하는 공용 통로는 아닙니다. 나누려는 개념이 독립적인지, 합치는 편이 맞는지부터 확인합니다.

## 슬라이스의 크기와 내부 구조

### 독립적인 생명주기로 슬라이스 나누기

프로젝트의 메뉴 옵션과 재고는 메뉴 없이 별도로 조회하거나 변경하지 않았고, 같은 API 응답으로 함께 전달되었습니다. 각각을 엔티티로 만들면 메뉴를 이해하는 데 여러 슬라이스를 따라가야 하므로 메뉴 안에 두었습니다. API 응답 하나라는 사실만으로 경계를 확정한 것은 아니며, 독립적으로 쓰이는 생명주기와 변경 요구가 있는지를 함께 보았습니다.

장바구니와 주문은 반대로 나눴습니다. 장바구니는 결제 전 사용자가 수정하고, 주문은 생성 후 서버와 매장이 상태를 변경합니다. 담기만 하고 떠나면 주문은 없고, 주문이 생성된 뒤 장바구니를 비워도 주문 기록은 남아야 합니다. 두 개체를 같은 상태로 관리하면 이 차이를 표현하기 어렵습니다.

매퍼도 이름보다 입력과 사용처를 봅니다. 메뉴와 장바구니를 가져와 주문 요청을 만드는 함수는 여러 개체를 연결하는 결제 절차에 속합니다. 이처럼 한 화면의 결제 절차에서만 사용하는 조합은 `pages/cart/model/checkout`에 둘 수 있습니다. 반면 주문 API의 응답을 주문 모델로 바꾸는 매퍼는 `entities/order/api`에 둘 수 있으므로, 매퍼라는 이름만으로 위치를 결정하지 않습니다.

### 세그먼트와 공개 API 구성

[슬라이스와 세그먼트 문서](https://feature-sliced.design/docs/reference/slices-segments)는 `ui`, `api`, `model`, `lib`, `config`를 대표적인 세그먼트로 소개합니다. `hooks`, `types`, `components`처럼 구현 형태를 나타내는 이름보다 목적을 드러내는 이름을 권합니다. 장바구니 안에서 훅인지 함수인지 먼저 나누기보다, 업무 상태와 조건이면 `model`, 화면 표현이면 `ui`, 서버 통신이면 `api`로 구분하는 방식입니다.

결제하기를 한 화면의 책임으로 두면 다음처럼 구성할 수 있습니다.

```text
src/
  pages/cart/
    ui/CartPage.tsx
    model/checkout/
      buildOrderRequest.ts
      useCheckout.ts
    index.ts
  features/change-pickup-method/
    ui/PickupMethodControl.tsx
    model/changePickupMethod.ts
    index.ts
  entities/cart/
    model/
      cart.ts
      cartStore.ts
    index.ts
  entities/order/
    api/createOrder.ts
    model/order.ts
    index.ts
  shared/api/
    client.ts
    index.ts
```

[공개 API](https://feature-sliced.design/docs/reference/public-api)는 외부가 알아야 할 항목만 노출하고 내부 파일 배치가 바뀌어도 소비자를 보호하는 경계입니다. 페이지 안에서만 쓰는 결제 훅까지 페이지의 `index.ts`에 내보낼 필요는 없습니다. 피처를 페이지로 옮길 때도 화면과 전용 훅을 함께 옮기면, 외부에는 페이지 컴포넌트만 공개할 수 있습니다.

관련 슬라이스를 `features/menu` 같은 그룹으로 묶더라도 그 안에 `_shared`를 만들어 코드를 공유하지 않습니다. 그룹은 탐색을 돕는 묶음이며 새 의존성 계층이 아닙니다. 공통 코드가 생겼다면 하위 도메인의 책임인지, 두 슬라이스를 합쳐야 하는지 다시 판단합니다.

## 배치 후 점검

- 페이지 전용 UI와 흐름을 별도 피처로 감싸기만 하지는 않았는지 확인합니다.
- 엔티티가 확인창·라우팅·특정 화면의 진행 순서까지 알고 있다면 상위 흐름으로 분리합니다.
- 피처가 다른 피처의 스토어를 참조한다면 상태의 소유권과 상위 조립 가능성을 검토합니다.
- 슬라이스 외부에서는 내부 경로 대신 공개 API를 사용합니다.
- 이름을 바꾸거나 폴더를 나눈 뒤에도 같은 코드들을 항상 함께 수정한다면 경계를 다시 확인합니다.

제가 적용하려는 기준은 개체의 조건과 사용자 절차를 구분하되, 재사용 범위가 확인되기 전에는 페이지 안에서 책임을 나누는 것입니다. “규칙은 엔티티, 흐름은 피처”에 **한 페이지의 흐름은 페이지에 둔다**는 조건을 함께 적용합니다.
