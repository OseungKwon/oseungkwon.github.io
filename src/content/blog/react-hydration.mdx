Next.js App Router에서 페이지에 처음 접속하거나 새로고침하면, 서버가 만든 HTML을 먼저 받아 화면을 표시할 수 있습니다. 클릭을 처리하는 Client Component도 이 첫 HTML에 포함될 수 있지만, HTML만으로 React의 클릭 핸들러까지 동작하지는 않습니다. 브라우저에서 해당 컴포넌트 코드를 실행해 기존 DOM에 연결하는 과정이 hydration입니다.

이 글은 서버가 미리 렌더링한 카운터를 브라우저에서 클릭할 수 있게 되는 과정을 다룹니다. Next.js가 구성하는 HTML 생성과 브라우저 연결을 살펴보기 위해, 본문에서는 React의 `renderToString`과 `hydrateRoot`를 직접 사용하는 예제로 풀어 보겠습니다. Next.js 프로젝트에서 이 진입 코드를 직접 작성한다는 뜻은 아니며, `data-initial-count`도 초기 데이터의 전달 경로를 드러내기 위해 예제에서 정한 방식입니다.

여기서 서버는 데이터를 반환하는 백엔드 API 서버가 아니라, Next.js처럼 React 화면을 미리 렌더링하는 실행 환경을 뜻합니다. Server Component와 Client Component가 이 과정에서 맡는 역할은 마지막 부록에서 본문의 카운터와 연결해 설명합니다.

## 서버에서 만드는 HTML

다음 카운터는 클릭하면 상태를 1씩 늘립니다. 서버에서 이 컴포넌트를 렌더링하면 버튼의 HTML이 만들어지지만, 이벤트 핸들러 함수까지 HTML에 담기는 것은 아닙니다.

```tsx
// Counter.tsx
import { useState } from 'react';

export default function Counter({ initialCount }: { initialCount: number }) {
  const [count, setCount] = useState(initialCount);

  return (
    <button onClick={() => setCount((current) => current + 1)}>
      {`증가 ${count}`}
    </button>
  );
}
```

`renderToString`은 컴포넌트 실행 결과를 HTML 문자열로 만듭니다. 카운터의 초기값은 HTML뿐 아니라 브라우저 코드에도 필요하므로 root 요소의 `data-initial-count` 속성에 함께 담겠습니다. [renderToString](https://react.dev/reference/react-dom/server/renderToString)

```tsx
// server.tsx
import { renderToString } from 'react-dom/server';
import Counter from './Counter';

export function renderPage() {
  const initialCount = 0;
  const markup = renderToString(<Counter initialCount={initialCount} />);

  return `<!doctype html>
<html lang="ko">
  <head><meta charset="utf-8"><title>카운터</title></head>
  <body>
    <div id="root" data-initial-count="${initialCount}">${markup}</div>
    <script type="module" src="/client.js"></script>
  </body>
</html>`;
}
```

root 안에는 `<button>증가 0</button>`이 들어갑니다. 브라우저는 이 HTML을 파싱해 DOM을 만들고 버튼을 그릴 수 있지만, 아직 React의 클릭 동작을 실행할 코드는 연결되지 않았습니다. `data-initial-count`에 담은 0은 애플리케이션이 직접 전달한 숫자이며, React의 Hook 상태 객체를 저장한 것이 아닙니다.

`/client.js`는 React와 카운터를 불러오는 브라우저용 진입 코드의 빌드 결과입니다. 브라우저가 이 코드를 로드하면 화면에 동작을 연결할 수 있습니다. Next.js 같은 프레임워크에서는 HTML 응답과 브라우저용 코드 전달을 프레임워크가 구성합니다.

## 브라우저에서 기존 DOM에 연결하기

브라우저 진입 코드에서는 root의 `data-initial-count`를 읽어 첫 렌더링에 사용합니다. HTML을 만들 때 사용한 값과 같은 값으로 `Counter`를 실행해야 서버가 만든 버튼에 연결할 수 있습니다.

```tsx
// client.tsx → 빌드 후 /client.js로 제공합니다.
import { hydrateRoot } from 'react-dom/client';
import Counter from './Counter';

const root = document.getElementById('root');
if (!root) throw new Error('root 요소가 없습니다.');

// 서버가 HTML에 함께 담은 초기값을 읽습니다.
const initialCount = Number(root.dataset.initialCount);
hydrateRoot(root, <Counter initialCount={initialCount} />);
```

> **Hydration:** 서버에서 생성한 HTML에 React를 연결해 기존 DOM의 상태 업데이트와 이벤트 처리를 관리하기 시작하는 과정입니다.

`hydrateRoot`를 호출하면 브라우저에서도 `Counter` 함수가 실행되고 `useState`가 초기화됩니다. React는 이 실행으로 얻은 컴포넌트 트리를 기존 DOM에 대응시키며, 결과가 일치하면 버튼을 새로 만들어 교체하지 않고 재사용합니다. HTML을 보고 원래 컴포넌트나 이벤트 핸들러를 역으로 알아내는 것은 아니므로, 브라우저에도 컴포넌트 코드가 필요합니다. [hydrateRoot](https://react.dev/reference/react-dom/client/hydrateRoot)

연결된 버튼을 누르면 이벤트 핸들러가 `setCount`를 호출하고, React가 카운터를 다시 렌더링합니다. 새 상태 1로 계산한 결과는 commit 단계에서 DOM에 반영되어 버튼의 텍스트가 `증가 1`로 바뀝니다. 이 업데이트에는 서버에서 HTML을 다시 받아오는 과정이 필요하지 않습니다. [Render and Commit](https://react.dev/learn/render-and-commit)

| 단계                   | 브라우저에 있는 것                     | 카운터의 상태                 |
| ---------------------- | -------------------------------------- | ----------------------------- |
| HTML 도착              | 서버가 만든 버튼 DOM                   | `증가 0`이 보임               |
| hydration 진행         | DOM과 브라우저에서 실행되는 React 코드 | 같은 초기값 0으로 연결        |
| hydration 완료 후 클릭 | React가 관리하는 버튼                  | 상태가 1로 바뀌고 텍스트 갱신 |

서버 HTML이 없는 화면에서 `createRoot`를 사용하는 것과도 구분해야 합니다. `createRoot`는 React 화면을 새로 구성할 때, `hydrateRoot`는 React가 서버에서 렌더링한 HTML을 이어서 사용할 때 선택합니다. 프레임워크를 사용한다면 이 선택은 대개 프레임워크의 진입 코드에서 처리합니다.

### 화면이 보이는 시점과 클릭할 수 있는 시점

앞의 카운터에서 `/client.js` 다운로드가 늦어지면, 브라우저에는 `증가 0`이 보이지만 버튼을 눌러도 숫자가 바뀌지 않는 구간이 생깁니다. HTML에는 버튼의 모양과 텍스트가 있지만 `onClick` 함수는 들어 있지 않기 때문입니다. React와 `Counter` 코드가 실행되고 해당 버튼의 hydration이 끝나야 클릭에 따른 상태 업데이트가 가능합니다.

이 차이는 개발자 도구에서 `/client.js` 요청을 차단한 뒤 새로고침하면 확인할 수 있습니다. 버튼은 그대로 표시되지만 클릭해도 0이 유지되고, 차단을 해제해 다시 접속하면 클릭할 때 숫자가 증가합니다. SSR로 첫 화면을 먼저 보여주더라도, React가 담당하는 상호작용에는 브라우저용 코드의 다운로드와 실행이 필요합니다. 링크 이동이나 폼 제출처럼 HTML 자체가 제공하는 기본 동작과는 구분해야 합니다.

### 같은 DOM인지 확인하기

DOM을 재사용한다는 설명은 버튼 객체를 비교해 확인할 수 있습니다. 앞의 `client.tsx`를 다음 코드로 바꾸면, hydration 전에 저장한 버튼과 연결 이후의 버튼을 비교합니다. `useEffect`에서 비교하는 이유는 `hydrateRoot`의 반환만으로 해당 트리의 hydration이 끝났다고 판단할 수 없기 때문입니다.

```tsx
// client.tsx
import { useEffect } from 'react';
import { hydrateRoot } from 'react-dom/client';
import Counter from './Counter';

const root = document.getElementById('root');
if (!root) throw new Error('root 요소가 없습니다.');

// React가 연결되기 전에 브라우저가 만든 버튼을 보관합니다.
const buttonBefore = root.querySelector('button');
if (!buttonBefore) throw new Error('서버가 만든 버튼이 없습니다.');

const initialCount = Number(root.dataset.initialCount);

function HydrationCheck() {
  useEffect(() => {
    console.log(
      '같은 버튼인가:',
      buttonBefore === document.querySelector('#root button'),
    );
  }, []);

  return <Counter initialCount={initialCount} />;
}

hydrateRoot(root, <HydrationCheck />);
```

서버와 브라우저의 결과가 일치하는 이 예제에서는 비교 결과가 `true`입니다. `HydrationCheck`는 별도의 DOM 요소를 추가하지 않으므로, 서버가 만든 버튼 구조를 유지합니다. 브라우저에서 `Counter`가 다시 실행되어도 기존 버튼 객체는 그대로 사용하며, 이후 클릭으로 상태가 바뀌면 그 버튼의 텍스트를 갱신합니다. 컴포넌트 함수를 실행하는 것과 DOM 요소를 새로 만드는 것은 같은 작업이 아닙니다.

## 첫 화면을 결정한 데이터 전달

서버와 브라우저는 각각 자신의 메모리에서 카운터를 실행합니다. 브라우저가 서버의 Hook 상태를 이어받는 대신, 전달받은 `initialCount`로 상태를 초기화해 같은 첫 화면을 만듭니다. 서버가 API에서 저장된 값 7을 조회했다면 화면에 표시할 값과 브라우저에 전달할 값 모두 7이어야 합니다.

앞의 `renderPage`에서 `initialCount`를 7로 바꾸면 root 부분은 다음과 같이 만들어집니다. 브라우저 코드는 바꾸지 않아도 속성에서 7을 읽어 `useState`의 초기값으로 사용합니다.

```html
<div id="root" data-initial-count="7"><button>증가 7</button></div>
```

화면의 텍스트는 7로 바꾸면서 `data-initial-count`에는 0을 넣으면, 브라우저는 여전히 `증가 0`을 기대합니다. DOM에 보이는 숫자를 React가 상태로 읽어 주는 것이 아니기 때문입니다. 데이터가 객체나 목록으로 커지면 프레임워크가 제공하는 직렬화·데이터 전달 방식을 사용하되, 서버와 브라우저가 같은 초기 데이터를 사용해야 한다는 조건은 같습니다.

[TanStack Query 글](/post/tanstack-query-beyond-use-query/#서버에서-먼저-조회하고-브라우저로-넘길-때)에서 다룬 캐시 hydration은 초기 데이터를 전달하는 한 방법입니다. query 캐시에는 서버의 조회 결과를 복원하고, React는 그 데이터를 읽어 만든 컴포넌트 트리를 DOM에 연결합니다. 두 과정은 복원하는 대상이 다릅니다.

## Hydration mismatch의 원인과 수정

브라우저 저장소에 있는 값을 카운터의 초기값으로 사용하면 서버와 브라우저가 서로 다른 화면을 만들 수 있습니다. 서버에는 `localStorage`가 없으므로 0을 사용하고, 브라우저에서는 저장된 7을 읽는 경우입니다.

```tsx
const [count, setCount] = useState(() => {
  if (typeof window === 'undefined') return 0;

  // 서버는 0으로 렌더링했는데 브라우저는 7로 시작할 수 있습니다.
  return Number(localStorage.getItem('count') ?? 0);
});
```

`window` 존재 여부를 확인하면 서버 실행 중 참조 오류는 피할 수 있습니다. 하지만 이 경우 서버 HTML은 `증가 0`, 브라우저가 기대하는 첫 화면은 `증가 7`이므로 서로 일치하지 않습니다. 서버에서 실행 가능한 코드인지와 양쪽의 첫 결과가 같은지는 따로 확인해야 합니다.

이런 불일치를 **hydration mismatch**라고 합니다. React는 불일치를 버그로 다루도록 안내하며, 복구 과정에서 해당 트리를 클라이언트에서 다시 렌더링할 수 있습니다. 모든 속성 차이를 자동으로 고쳐 준다고 보장하지 않으므로, 서버 HTML과 브라우저의 첫 렌더링을 비교해 원인을 찾아야 합니다. 연결이 끝난 뒤 클릭이나 Effect로 화면이 바뀌는 것은 이 불일치에 해당하지 않습니다. [Hydration mismatch](https://react.dev/reference/react-dom/client/hydrateRoot#caveats)

저장된 값이 7일 때 위 예제에서 비교할 대상은 다음과 같습니다.

| 확인 대상                                | 값 또는 결과              |
| ---------------------------------------- | ------------------------- |
| 서버가 응답한 버튼 HTML                  | `<button>증가 0</button>` |
| 브라우저의 `useState` 초기화에서 읽은 값 | `localStorage`의 `7`      |
| 브라우저가 첫 렌더링에서 기대하는 버튼   | `<button>증가 7</button>` |

개발자 도구의 Network에서 HTML 문서의 응답을 보면 서버가 보낸 0을 확인할 수 있습니다. 반면 Elements에는 React의 복구나 이후 업데이트까지 반영된 DOM이 보이므로, 이미 7로 바뀐 화면만 보고 양쪽이 처음부터 일치했다고 판단해서는 안 됩니다. 이 예제에서는 서버 응답의 0과 브라우저 초기화 코드가 읽은 7을 비교해야 원인이 드러납니다.

### 브라우저 저장값의 반영 시점

서버가 알 수 없는 저장값이라면 처음에는 양쪽 모두 0을 렌더링하고, 브라우저에 연결된 뒤 저장소를 읽을 수 있습니다. `useEffect`는 서버 렌더링 중에는 실행되지 않습니다. [서버와 클라이언트에서 다른 내용 표시하기](https://react.dev/reference/react/useEffect#displaying-different-content-on-the-server-and-the-client)

```tsx
import { useEffect, useState } from 'react';

export default function SavedCounter() {
  // 서버와 브라우저의 첫 화면을 0으로 맞춥니다.
  const [count, setCount] = useState(0);

  useEffect(() => {
    const saved = localStorage.getItem('count');
    if (saved === null) return;

    const value = Number(saved);
    if (Number.isFinite(value)) setCount(value);
  }, []);

  return (
    <button onClick={() => setCount((current) => current + 1)}>
      {`증가 ${count}`}
    </button>
  );
}
```

브라우저에서는 0으로 연결한 뒤 별도의 상태 업데이트로 7을 표시합니다. 이 방식은 mismatch를 피하지만, 저장값이 적용되기 전의 0이 잠깐 보일 수 있습니다. 첫 화면부터 저장값이 필요하다면 서버에서도 읽을 수 있는 데이터로 전달하거나, 값이 준비될 때까지 해당 영역을 로딩 상태로 표시하는 쪽을 검토해야 합니다.

hydration에서 일치해야 하는 것은 서버 HTML과 브라우저의 첫 렌더링 결과입니다. 두 번째 방식의 0에서 7로 바뀌는 과정은 연결 이후 React가 수행하는 상태 업데이트이므로, 첫 결과의 불일치를 복구하는 작업과는 다릅니다.

### 시간과 HTML 구조의 차이

렌더링 중 `Date.now()`나 `Math.random()`을 호출하면 서버와 브라우저가 서로 다른 시각이나 값을 사용할 수 있습니다. 같은 날짜 데이터도 각 환경의 기본 시간대나 locale로 포맷하면 텍스트가 달라질 수 있으므로, 값뿐 아니라 표시 형식도 맞춰야 합니다. 첫 화면에 필요한 값과 포맷 조건은 서버에서 정해 전달하고, 브라우저에서만 필요한 값은 연결 이후에 반영할 수 있습니다. [Components and Hooks must be pure](https://react.dev/reference/rules/components-and-hooks-must-be-pure)

서버가 생성한 HTML 구조 자체도 확인해야 합니다. 예를 들어 `<p>` 안에 `<div>`를 넣으면 브라우저의 HTML 파서가 DOM 구조를 보정할 수 있습니다. 이 경우 React가 기대하는 중첩 관계와 브라우저가 만든 DOM이 달라지므로, 값 비교만으로 원인을 찾을 수 없습니다.

`suppressHydrationWarning`은 차이가 불가피한 특정 요소의 경고를 억제하는 옵션입니다. 한 단계 깊이에만 적용되며, 불일치한 텍스트를 React가 고쳐 주도록 만드는 옵션은 아닙니다. 저장소 초기화나 잘못된 HTML 구조를 해결하는 대신 넓게 적용해서는 안 됩니다. [suppressHydrationWarning](https://react.dev/reference/react-dom/client/hydrateRoot#suppressing-unavoidable-hydration-mismatch-errors)

## 스트리밍과 선택적 hydration

카운터 예제는 화면 전체의 HTML을 한 번에 만들었지만, 매장 상세와 리뷰 목록을 함께 보여주는 페이지에서는 리뷰 응답이 더 늦을 수 있습니다. 스트리밍 SSR은 먼저 준비된 화면과 리뷰의 fallback을 보내고, 리뷰가 준비되면 그 내용을 이어서 전달할 수 있습니다. Node.js에서는 `renderToPipeableStream`이 이 방식을 지원합니다. [Streaming server rendering](https://react.dev/reference/react-dom/server/renderToPipeableStream#streaming-more-content-as-it-loads)

### 리뷰 영역을 별도로 기다리기

먼저 브라우저에서 리뷰 컴포넌트의 코드를 따로 내려받는 경우를 보겠습니다. `lazy`는 동적 import가 완료될 때까지 컴포넌트 렌더링을 대기시키고, `Suspense`는 그동안 표시할 fallback의 범위를 정합니다. 앞의 카운터는 리뷰 경계 밖에 두겠습니다.

```tsx
// StorePage.tsx
import { lazy, Suspense } from 'react';
import Counter from './Counter';

const Reviews = lazy(() => import('./Reviews'));

export default function StorePage() {
  return (
    <main>
      <h1>강남점</h1>
      <Counter initialCount={0} />

      {/* 리뷰가 준비되지 않아도 매장 이름과 카운터는 먼저 보여줍니다. */}
      <Suspense fallback={<p>리뷰를 불러오는 중입니다.</p>}>
        <Reviews />
      </Suspense>
    </main>
  );
}
```

`Reviews` 파일은 다음과 같이 클릭 동작이 있는 컴포넌트로 만들 수 있습니다. 서버에서 이 코드를 실행해 HTML을 만들었더라도, 브라우저에서 리뷰를 펼치려면 이 컴포넌트의 코드가 필요합니다.

```tsx
// Reviews.tsx
import { useState } from 'react';

export default function Reviews() {
  const [expanded, setExpanded] = useState(false);

  return (
    <section>
      <h2>리뷰</h2>
      <button onClick={() => setExpanded((current) => !current)}>
        {expanded ? '접기' : '리뷰 보기'}
      </button>
      {expanded && <p>음식이 따뜻하게 도착했습니다.</p>}
    </section>
  );
}
```

이 트리를 `renderToPipeableStream`으로 렌더링하고, 경계 밖의 화면이 준비되는 `onShellReady`에서 응답을 보내기 시작하면 서버는 리뷰를 기다리는 동안 매장 이름, 카운터, fallback을 먼저 보낼 수 있습니다. 리뷰 렌더링이 준비되면 나머지 HTML과 fallback을 교체하는 스크립트를 이어서 보냅니다. 서버에서도 리뷰가 이미 준비되어 있다면 기다리지 않고 함께 보낼 수 있으므로, `Suspense`가 있다고 항상 fallback이 보이는 것은 아닙니다. [스트리밍과 shell 구성](https://react.dev/reference/react-dom/server/renderToPipeableStream#specifying-what-goes-into-the-shell)

이 코드의 대기 원인은 `lazy`로 불러오는 컴포넌트 코드입니다. 리뷰 **데이터**를 기다리는 경우에도 같은 경계를 활용할 수 있지만, 데이터 조회가 Suspense와 연동되어 있어야 합니다. `useEffect` 안에서 실행한 `fetch`를 `Suspense`로 감싸는 것만으로 서버가 해당 데이터를 기다리거나 스트리밍하지는 않습니다. [Suspense를 활성화하는 조건](https://react.dev/reference/react/Suspense#what-activates-a-suspense-boundary)

### HTML 도착과 hydration의 순서

서버에서 리뷰 HTML을 받았더라도, 브라우저의 리뷰 코드 다운로드가 늦을 수 있습니다. 이때 매장 이름과 카운터를 처리할 코드가 준비되어 있다면 React는 리뷰 경계의 hydration을 기다리지 않고 카운터부터 연결할 수 있습니다. 리뷰 경계의 코드가 준비되면 해당 영역도 연결하며, 사용자가 상호작용하려는 영역의 hydration에 우선순위를 둘 수도 있습니다. 이를 **선택적 hydration**(selective hydration)이라고 합니다. [Suspense](https://react.dev/reference/react/Suspense#caveats)

실제 도착 순서는 네트워크와 각 영역의 준비 상태에 따라 달라집니다. 스트리밍은 HTML의 전달을 나누고, 선택적 hydration은 브라우저의 연결 작업을 나누므로 리뷰 HTML이 보이는 시점과 리뷰 버튼이 동작하는 시점도 달라질 수 있습니다.

## 부록: Next.js의 Server Component와 hydration

본문의 `Counter`는 서버에서 HTML을 만들 때도 실행되고, 브라우저에서 그 HTML에 연결할 때도 실행됩니다. Next.js App Router에서는 이 카운터가 Client Component에 해당합니다. 서버에서 HTML을 만들었다는 사실만으로 Server Component가 되는 것은 아니며, 두 컴포넌트를 구분하려면 브라우저에서도 해당 코드를 실행하는지 살펴봐야 합니다.

### 매장 페이지와 카운터 나누기

매장 이름을 표시하는 페이지와 클릭에 반응하는 카운터를 나눠 보겠습니다. App Router의 페이지는 기본적으로 Server Component이므로, 다음 `StorePage`의 구현 코드는 브라우저에 보내 실행하지 않습니다. 대신 이 함수가 반환한 화면 구성에 카운터를 포함할 수 있습니다. [Server Component와 상호작용 영역](https://react.dev/reference/rsc/server-components#adding-interactivity-to-server-components)

```tsx
// app/page.tsx
import Counter from './Counter';

export default function StorePage() {
  return (
    <main>
      <h1>강남점</h1>
      {/* 브라우저에서 클릭을 처리할 컴포넌트에 초기값을 전달합니다. */}
      <Counter initialCount={0} />
    </main>
  );
}
```

`Counter`에는 브라우저에서 유지할 상태와 클릭 핸들러가 필요합니다. 이 파일 맨 위에 `'use client'`를 붙이면 Client Component의 경계를 선언할 수 있습니다.

```tsx
// app/Counter.tsx
'use client';

import { useState } from 'react';

export default function Counter({ initialCount }: { initialCount: number }) {
  const [count, setCount] = useState(initialCount);

  return (
    <button onClick={() => setCount((current) => current + 1)}>
      {`증가 ${count}`}
    </button>
  );
}
```

`'use client'`는 해당 컴포넌트를 브라우저에서만 렌더링하라는 지시가 아닙니다. 이 선언은 컴포넌트와 그 의존 코드를 브라우저에서도 실행할 수 있도록 Client Component의 경계를 정합니다. 첫 접속에서는 Next.js가 이 카운터도 서버에서 렌더링해 초기 HTML을 만들 수 있습니다. [Next.js의 Client Component](https://nextjs.org/docs/app/getting-started/server-and-client-components#using-client-components)

Client Component까지 서버에서 렌더링하는 이유는 클릭에 반응하는 영역도 첫 화면에 함께 보여주기 위해서입니다. 카운터를 브라우저에서만 만든다면 서버 HTML에는 매장 이름만 있고, JavaScript를 내려받아 실행한 뒤에야 버튼이 나타납니다. 반면 서버가 `<button>증가 0</button>`까지 만들어 보내면 브라우저는 카운터 코드의 실행을 기다리지 않고 매장 이름과 버튼을 함께 표시할 수 있습니다. 이후 hydration을 거쳐 클릭 동작을 연결합니다. [Next.js의 첫 페이지 로드](https://nextjs.org/docs/app/getting-started/server-and-client-components#on-the-client-first-load)

이때 서버에서는 `Counter`를 초기값 0으로 실행해 버튼 HTML을 만듭니다. 클릭 핸들러를 실행하거나 `useEffect`를 실행하는 것은 아닙니다. 컴포넌트의 렌더링 코드는 서버에서도 실행되므로, `'use client'`가 있어도 초기 렌더링에서 `localStorage`를 읽으면 본문에서 살펴본 참조 오류나 mismatch가 발생할 수 있습니다.

### 첫 접속에서 전달되는 HTML과 컴포넌트 정보

HTML만으로는 React가 카운터의 위치와 초기값을 알아낼 수 없다는 점은 Next.js에서도 같습니다. 본문의 예제는 `Counter`를 직접 불러오고 `data-initial-count`에서 0을 읽었지만, App Router에서는 Next.js가 컴포넌트 정보와 props를 전달합니다. 위 페이지가 브라우저에서 동작하기까지의 순서는 다음과 같습니다.

1. **Server Component의 결과를 만듭니다.** 서버에서 `StorePage`를 실행하면 `강남점`을 표시할 요소와 `Counter`가 들어갈 위치가 정해집니다. Next.js는 이 결과에 Client Component 코드의 참조와 `initialCount: 0` 같은 props를 담습니다. 이 정보를 전달하는 형식이 **RSC Payload**입니다.
2. **첫 화면의 HTML을 만듭니다.** Next.js는 RSC Payload와 Client Component를 이용해 초기 HTML을 렌더링합니다. 이때 `Counter`도 초기값 0으로 렌더링되므로, 브라우저는 매장 이름과 `증가 0` 버튼을 먼저 표시할 수 있습니다.
3. **브라우저에서 카운터를 수화합니다.** React는 RSC Payload로 Server Component의 결과와 Client Component의 배치를 맞추고, 내려받은 `Counter` 코드를 실행해 기존 버튼에 연결합니다. 이때도 초기값은 0이며, 이후 클릭하면 브라우저의 상태가 1로 바뀝니다.

아래 그림은 서버에서 만든 컴포넌트 정보가 초기 HTML과 브라우저의 수화로 이어지는 과정을 보여줍니다.

`StorePage`는 브라우저에서 다시 실행되지 않고 서버에서 전달한 결과가 사용됩니다. 반면 `Counter`는 서버에서 만든 HTML을 브라우저에서 이어서 사용하므로, 본문에서 설명한 첫 렌더링의 일치 조건과 hydration이 그대로 적용됩니다. [Next.js의 서버 렌더링과 첫 페이지 로드](https://nextjs.org/docs/app/getting-started/server-and-client-components#how-do-server-and-client-components-work-in-nextjs)

이후 앱 안에서 다른 페이지로 이동할 때는 Next.js가 RSC Payload를 가져오거나 캐시에서 사용해 화면을 갱신합니다. 이때 Client Component는 브라우저에서 렌더링하므로, 첫 접속처럼 새 HTML 문서를 받아 연결하는 과정과 구분해야 합니다. [클라이언트 내 페이지 이동](https://nextjs.org/docs/app/getting-started/server-and-client-components#subsequent-navigations)
