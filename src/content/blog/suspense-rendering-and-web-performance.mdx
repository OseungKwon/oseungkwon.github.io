## Suspense를 사용하는 이유

로딩 상태에 따라 UI를 나누는 방법으로는 `if (isLoading)` 같은 조건문이 있습니다. 이 조건을 각 컴포넌트에 두면 컴포넌트마다 로딩 화면을 보여줄 수 있지만, 여러 컴포넌트가 준비된 뒤 함께 나타나게 하려면 상위에서 로딩 상태를 모아 판단해야 합니다.

[**Suspense**](https://react.dev/reference/react/Suspense)는 하위 컴포넌트가 렌더링을 완료하지 못했을 때 보여줄 UI를 상위에서 지정하게 해 줍니다. 같은 경계 안의 컴포넌트는 함께 표시하고, 따로 기다려도 되는 영역은 별도 경계로 나눌 수 있습니다.

상품명과 가격은 이미 준비되어 있고, 추천 상품은 기다리는 상황을 예로 들겠습니다. 추천 상품을 감싼 Suspense에 로딩 UI를 지정하면 상품 정보는 보여주면서 추천 영역의 렌더링을 기다릴 수 있습니다.

> **Suspense 경계**는 `<Suspense>`로 감싼 영역입니다. 그 안의 콘텐츠를 아직 보여줄 수 없을 때 대신 표시할 UI를 `fallback`으로 지정합니다. 아래 예제의 fallback은 ‘추천 상품을 불러오는 중입니다.’라는 문구입니다.

```tsx
import { Suspense } from 'react';

type Item = { id: string; name: string };

type ProductDetailProps = {
  product: { name: string; price: number };
  itemsPromise: Promise<Item[]>;
};

function ProductDetail({ product, itemsPromise }: ProductDetailProps) {
  return (
    <main>
      <h1>{product.name}</h1>
      <p>{product.price}원</p>

      {/* 추천 상품을 기다리는 동안 이 영역에만 로딩 UI를 표시합니다. */}
      <Suspense fallback={<p>추천 상품을 불러오는 중입니다.</p>}>
        <Recommendations itemsPromise={itemsPromise} />
      </Suspense>
    </main>
  );
}
```

`itemsPromise`는 외부에서 시작한 추천 상품 요청의 Promise입니다. **Promise**는 나중에 끝날 작업의 결과를 나타내는 JavaScript 객체로, 여기서는 아직 도착하지 않은 추천 상품 목록을 다룹니다. Suspense는 요청을 시작하지 않고, 하위 컴포넌트가 결과를 기다린다고 알렸을 때 fallback을 표시합니다.

## `use`로 Promise의 결과 읽기

> [`use`](https://react.dev/reference/react/use)는 렌더링 중에 Promise 같은 리소스의 값을 읽는 React API입니다. React 19에서 `use(itemsPromise)`를 호출하면, 완료된 추천 상품 목록을 읽거나 아직 준비되지 않았다는 사실을 React에 알릴 수 있습니다.

`Recommendations`는 로딩 상태를 직접 검사하는 대신 `use`로 결과를 읽습니다. 값을 얻었다면 그 아래 코드에서 목록을 만들고, 기다려야 한다면 React가 상위 Suspense 경계를 처리하도록 맡깁니다.

```tsx
import { use } from 'react';

function Recommendations({ itemsPromise }: { itemsPromise: Promise<Item[]> }) {
  const items = use(itemsPromise);

  return (
    <ul>
      {items.map((item) => (
        <li key={item.id}>{item.name}</li>
      ))}
    </ul>
  );
}
```

| Promise의 상태 | `use(itemsPromise)`의 동작           | `Recommendations`의 실행              |
| -------------- | ------------------------------------ | ------------------------------------- |
| 대기 중        | 렌더링을 중단하는 신호를 전달합니다. | 아래의 `return`에 도달하지 못합니다.  |
| 성공           | 결과를 반환합니다.                   | `items`로 목록을 계산합니다.          |
| 실패           | 거부 사유를 오류로 던집니다.         | 오류를 처리할 상위 경계가 필요합니다. |

렌더링을 완료하는 데 필요한 값이 없어 중단되는 것을 **Suspend**라고 부릅니다. 위 예제에서는 `use`가 목록을 돌려주지 못해 `return`까지 실행하지 못한 상태입니다. Effect나 이벤트 핸들러에서 실행한 일반적인 `fetch`는 Suspense가 감지하지 않으므로, 그런 컴포넌트를 감싸는 것만으로 fallback이 나타나지는 않습니다.

### 내부에서는 무엇을 던질까

이하의 내부 구현은 **React v19.0.0의 클라이언트 렌더러**를 기준으로 살펴보겠습니다. 렌더러는 컴포넌트를 호출해 UI를 계산하고 화면에 반영하는 React의 내부 코드입니다. `use`가 Promise를 읽는 경로에서는 Promise 자체를 그대로 던지는 대신, Promise를 별도로 기록하고 `SuspenseException`이라는 내부 신호를 던집니다.

[`ReactFiberThenable.js`의 `trackUsedThenable`](https://github.com/facebook/react/blob/v19.0.0/packages/react-reconciler/src/ReactFiberThenable.js)에서 대기 중인 Promise를 처리하는 부분입니다. 개발 모드 코드를 생략하고 주석을 덧붙였습니다.

```js
// 렌더러가 대기 중인 Promise를 따로 가져갈 수 있게 기록합니다.
suspendedThenable = thenable;
throw SuspenseException;
```

`throw`를 실행했으므로 현재 호출 중인 `Recommendations`는 목록을 반환하지 못하고 빠져나옵니다. React의 렌더러는 이 신호를 받아 `getSuspendedThenable()`로 기록해 둔 Promise를 가져옵니다. 이 과정은 [`ReactFiberWorkLoop.js`의 `handleThrow`](https://github.com/facebook/react/blob/v19.0.0/packages/react-reconciler/src/ReactFiberWorkLoop.js)에서 확인할 수 있습니다.

따라서 `use`를 `try/catch`로 감싸면 이 내부 신호를 사용자 코드가 먼저 잡을 수 있습니다. React가 `use`를 `try/catch` 안에서 호출하지 않도록 안내하는 이유입니다.

요청 실패는 상위의 [**Error Boundary**](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary)에서 처리할 수 있습니다. Error Boundary는 하위 컴포넌트의 렌더링 오류를 받아 실패 화면을 보여주는 컴포넌트입니다. 예를 들어 추천 상품 조회가 실패하면 목록 자리에 ‘다시 시도해 주세요.’를 표시하도록 구성할 수 있습니다.

오류 화면 대신 기본 목록을 보여주려면 Promise의 `catch`에서 대체 값을 반환하는 방법도 있습니다.

## Suspense 경계에서 fallback을 렌더링하기

React는 중단된 컴포넌트를 처리할 수 있는 가장 가까운 Suspense 경계를 선택합니다. 앞의 예제에서는 `Recommendations`를 감싼 경계가 해당하며, 상품명과 가격은 그 경계 밖에 있습니다.

[`ReactFiberThrow.js`의 `throwException`](https://github.com/facebook/react/blob/v19.0.0/packages/react-reconciler/src/ReactFiberThrow.js)은 현재 경계를 가져와 중단을 처리하도록 표시합니다. 관련 호출만 발췌했습니다.

```js
const suspenseBoundary = getSuspenseHandler();

markSuspenseBoundaryShouldCapture(
  suspenseBoundary,
  returnFiber,
  sourceFiber,
  root,
  rootRenderLanes,
);
```

이 호출은 DOM을 즉시 로딩 화면으로 바꾸지 않습니다. 해당 경계에서 fallback을 렌더링하도록 표시하고, React는 그 결과를 화면에 반영할 때 DOM을 변경합니다. 컴포넌트를 호출해 UI를 계산하는 **렌더 단계**와 계산한 결과를 DOM에 반영하는 **커밋 단계**가 구분되어 있기 때문입니다.

추천 상품을 처음 보여주는 경우, 목록을 계산할 수 없으므로 fallback을 렌더링하고 커밋할 수 있습니다. 이때 화면에는 상품명·가격과 함께 “추천 상품을 불러오는 중입니다.”가 나타납니다.

### 경계의 위치가 대기 범위를 바꾸는 이유

같은 Suspense 안에 추천 상품과 리뷰를 넣으면, 하나가 Suspend되어도 그 경계는 하위 콘텐츠 대신 fallback을 보여줍니다. 추천 상품이 먼저 준비되었더라도 리뷰가 준비되지 않았다면 둘을 함께 표시할 수 없습니다. 각각 Suspense로 감싸면 두 영역은 독립적으로 나타날 수 있습니다.

추천 상품이 먼저 준비된 시점의 화면을 나란히 놓으면 경계의 차이가 드러납니다.

fallback도 렌더링할 컴포넌트입니다. fallback 자체가 Suspend되면 그 경계는 대체 UI마저 완료할 수 없으므로, React가 상위 Suspense 경계를 사용합니다. “가장 가까운 경계”는 JSX에서 가까워 보이는 위치가 아니라, 현재 중단을 받아 처리할 수 있는 상위 경계를 가리킵니다.

## Promise가 완료되면 렌더링을 다시 시도합니다

React는 대기 중인 Promise가 완료되는 시점에 알림을 받도록 콜백을 등록합니다. 렌더링 중에는 컴포넌트 트리 전체의 작업을 관리하는 루트에 재시도가 필요하다고 알리는 콜백을 연결하고, fallback이 커밋된 경계에도 재시도 콜백을 연결합니다. 이 두 경로를 통해 fallback을 커밋하기 전이나 후에 Promise가 완료되는 경우를 처리합니다.

[`attachSuspenseRetryListeners`](https://github.com/facebook/react/blob/v19.0.0/packages/react-reconciler/src/ReactFiberCommitWork.js)의 콜백 등록 부분은 다음과 같습니다. 여기서 `wakeable`은 완료 알림을 받을 Promise를 가리킵니다.

```js
// 성공과 실패 모두 다음 렌더링에서 결과를 확인해야 합니다.
wakeable.then(retry, retry);
```

이 콜백은 Promise의 결과로 DOM을 직접 바꾸지 않습니다. React가 해당 경계의 렌더링을 다시 시도하도록 작업을 예약합니다. 이후 `Recommendations`를 다시 호출하면 같은 `use(itemsPromise)`를 실행하게 됩니다.

```tsx
function Recommendations({ itemsPromise }: { itemsPromise: Promise<Item[]> }) {
  // 재시도할 때도 이 줄을 다시 실행합니다.
  const items = use(itemsPromise);

  // Promise가 성공했다면 이번에는 목록을 반환할 수 있습니다.
  return (
    <ul>
      {items.map((item) => (
        <li key={item.id}>{item.name}</li>
      ))}
    </ul>
  );
}
```

`await` 뒤에서 함수 실행이 이어지는 것과 달리, 처음 마운트되기 전에 Suspend된 컴포넌트는 처음부터 다시 렌더링합니다. 이번에는 `use`가 완료된 값을 반환하므로 목록을 계산할 수 있고, React가 그 결과를 커밋하면 fallback이 추천 목록으로 바뀝니다.

Promise가 실패했을 때도 재시도는 필요합니다. 다시 실행한 `use`가 오류를 던지면 상위 Error Boundary가 실패 화면을 렌더링할 수 있습니다. Suspense의 fallback은 이 오류 화면을 대신하지 않습니다.

다음 데모에서는 Promise가 성공한 뒤에도 fallback이 남아 있다가, 다시 계산한 목록을 커밋할 때 화면이 바뀌는 과정을 확인할 수 있습니다.

### 재시도할 때 읽을 Promise는 유지되어야 합니다

컴포넌트가 다시 호출된다는 점은 Promise를 만드는 위치에도 영향을 줍니다. 다음처럼 클라이언트 컴포넌트 본문에서 요청을 시작하면, 재시도할 때마다 새로운 요청과 Promise를 만듭니다.

```tsx
function Recommendations({ productId }: { productId: string }) {
  // 컴포넌트를 다시 호출하면 완료된 Promise 대신 새 Promise를 만듭니다.
  const itemsPromise = getRecommendations(productId);
  const items = use(itemsPromise);
  return <RecommendationList items={items} />;
}
```

여기서 `getRecommendations`는 호출할 때마다 요청을 시작해 새 Promise를 반환하는 함수입니다. 첫 렌더링에서 Promise A를 만들었어도 다음 호출은 Promise B를 `use`에 전달합니다. React는 이처럼 캐시되지 않은 Promise로 Suspend하는 코드를 지원하지 않으며, 개발 모드에서 경고합니다.

앞의 예제가 `itemsPromise`를 외부에서 전달받도록 한 이유가 여기에 있습니다. 재시도에서도 같은 Promise를 읽을 수 있으면 이미 완료된 요청의 결과를 사용할 수 있습니다. React 문서에서는 서버 컴포넌트에서 Promise를 만들어 전달하거나, Suspense를 지원하는 라이브러리의 캐시를 사용하도록 안내합니다.

[`useMemo`](https://react.dev/reference/react/useMemo#caveats)는 계산 결과를 저장했다가 의존성이 바뀌지 않은 다음 렌더링에서 재사용하는 Hook입니다. 다만 여기에 Promise를 저장하는 것만으로는 최초 마운트의 재시도까지 보장할 수 없습니다. React는 최초 렌더링 중 Suspend된 컴포넌트의 `useMemo` 캐시를 버릴 수 있으므로, 다시 호출할 때 새 Promise가 만들어질 수 있습니다.

## 이미 표시한 콘텐츠가 다시 Suspend되는 경우

지금까지는 추천 목록을 처음 표시하는 상황을 살펴봤습니다. 목록이 보이는 상태에서 새로운 Promise를 전달받아 다시 Suspend되면, React는 같은 경계의 콘텐츠를 fallback으로 바꿀 수 있습니다.

**Transition**은 상태 업데이트를 긴급하지 않은 작업으로 표시하는 React의 기능입니다. 예를 들어 새 추천 목록을 준비하는 업데이트를 Transition으로 표시하면, React는 이미 보이는 목록을 유지하면서 새 목록의 렌더링을 기다릴 수 있습니다. 따라서 Suspend를 “무조건 즉시 fallback으로 바꾸는 동작”으로 이해하면 화면 전환에서의 동작을 설명하기 어렵습니다.

여기서도 대기 중인 Promise를 읽고, 완료 알림을 받아 렌더링을 다시 시도하는 과정은 같습니다. 달라지는 것은 그동안 화면에 무엇을 남겨 두느냐입니다. 처음 보여줄 콘텐츠가 없으면 fallback을 사용할 수 있고, 이미 보여준 콘텐츠가 있다면 업데이트 방식에 따라 그 콘텐츠를 유지할 수 있습니다.
