“주소창에 네이버를 입력하면 어떤 일이 일어날까?”처럼 URL 입력부터 화면 표시까지의 과정을 다룬 글을 자주 접했습니다. 최근 회사에서 인프라 작업을 많이 하다 보니, 브라우저가 보낸 요청이 네트워크와 인프라 안에서 어떤 경로로 전달되는지 궁금해져 이 글을 쓰게 되었습니다.

브라우저의 요청이 CDN과 로드 밸런서를 거쳐 앱에 전달되고, 응답이 돌아와 화면으로 표시되기까지의 흐름을 살펴보겠습니다.

## 상품 페이지의 요청 경로

가상의 상품 조회 서비스를 예로 들겠습니다. `my.example.com`에 상품·계정·로그인 앱을 연결하고, 상품 상세는 서버에서 HTML을 만드는 **SSR**(Server-Side Rendering)로 제공합니다.

사용자가 `https://my.example.com/products/42`를 열면 브라우저는 접속할 주소를 찾고 HTTPS 연결을 준비합니다. 이 서비스는 여러 지역의 서버로 콘텐츠를 전달하는 **CDN**(Content Delivery Network)을 사용합니다. 사용자와 가까운 네트워크에서 요청을 받도록 배치한 CDN 서버를 **엣지 서버**(edge server)라고 부릅니다. 요청은 이 서버에서 보안 검사와 캐시 조회를 거쳐, 저장된 응답으로 처리할 수 없을 때 상품 앱까지 전달됩니다. 상품 앱이 API에서 데이터를 가져와 HTML을 반환하면 브라우저는 CSS·JavaScript·이미지 등 추가 자원을 받아 화면을 구성합니다.

## DNS 조회와 주소 캐시

브라우저는 URL에서 접속할 호스트를 확인합니다. `https`는 통신 방식, `my.example.com`은 호스트, `/products/42`는 요청할 경로이며, **DNS**(Domain Name System)로 조회하는 대상은 이 중 호스트 이름입니다. `/products`와 `/account`를 보고 서로 다른 앱을 고르는 일은 이후 HTTP 요청을 읽는 라우터가 맡습니다.

브라우저나 운영체제의 캐시에 조회 결과가 남아 있으면 이를 재사용하고, 없으면 설정된 DNS 리졸버에 조회를 요청합니다. 이렇게 얻은 IP 주소가 브라우저가 연결할 대상이 됩니다. [MDN 브라우저 탐색 과정](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/How_browsers_work#dns_lookup)

> **DNS 리졸버란?**
>
> 리졸버(resolver)는 `my.example.com` 같은 이름에 대응하는 DNS 정보를 조회하는 소프트웨어입니다. 브라우저나 운영체제의 요청을 받아 대신 조회를 수행하는 서버를 **재귀 리졸버**라고 합니다. 재귀 리졸버는 자신의 캐시에 결과가 있으면 바로 응답하고, 없으면 루트·최상위 도메인·권한 DNS 서버 등을 조회해 결과를 반환합니다.

### A·AAAA: 이름에 연결된 IP 주소

DNS에는 이름별로 어떤 정보를 반환할지 정한 **레코드**(record)가 저장됩니다. 상품 서비스의 이름을 CDN에 연결하기 위해 다음 레코드를 설정했다고 가정하겠습니다.

| 조회할 이름        | 유형  | 반환할 값          |
| ------------------ | ----- | ------------------ |
| `my.example.com`   | CNAME | `edge.example.net` |
| `edge.example.net` | A     | `203.0.113.10`     |
| `edge.example.net` | AAAA  | `2001:db8::10`     |

A 레코드는 이름에 대응하는 IPv4 주소를 반환합니다. 위에서 `edge.example.net`의 A 레코드를 조회하면 `203.0.113.10`을 얻습니다. AAAA 레코드도 이름을 IP 주소에 연결하지만, 반환하는 값이 `2001:db8::10` 같은 IPv6 주소입니다. 두 유형이 모두 있으면 브라우저는 네트워크의 IPv4·IPv6 연결 가능 여부 등을 고려해 접속할 주소를 선택합니다.

> **왜 A와 AAAA로 이름이 다를까요?**
>
> A는 주소를 뜻하는 Address에서 왔습니다. IPv4 주소는 32비트이고 IPv6 주소는 그 네 배인 128비트이므로, IPv6용 레코드는 A를 네 번 쓴 AAAA라고 이름 붙였습니다. [Cloudflare의 A 레코드 설명](https://www.cloudflare.com/learning/dns/dns-records/dns-a-record/), [IPv6의 DNS 레코드](https://intronetworks.cs.luc.edu/current/uhtml/ipv6b.html)

### CNAME: 다른 이름을 따라 주소 찾기

`my.example.com`의 CNAME 값은 IP 주소가 아닌 `edge.example.net`입니다. 이는 상품 서비스 이름의 주소를 찾을 때 CDN이 제공한 이름을 따라가도록 한 설정입니다. 캐시에 결과가 없는 경우 조회는 다음과 같이 이어집니다.

1. 브라우저가 리졸버에 `my.example.com`의 IP 주소를 요청합니다.
2. 리졸버는 CNAME을 통해 `edge.example.net`을 확인합니다.
3. 이어서 `edge.example.net`의 A·AAAA 레코드를 조회해 IP 주소를 얻고 브라우저에 결과를 반환합니다.

브라우저는 얻은 IP 주소로 CDN 엣지에 연결하되, 주소창의 호스트는 `my.example.com`으로 유지합니다. CNAME은 DNS 조회에서 따라갈 이름을 지정하므로, 사용자가 접속하는 서비스 이름을 바꾸지 않고 CDN에 연결할 수 있습니다. [Cloudflare DNS 레코드 유형](https://developers.cloudflare.com/dns/manage-dns-records/reference/dns-record-types/)

### TTL: 조회한 결과를 재사용하는 시간

**TTL**(Time to Live)은 레코드 유형이 아니라 각 DNS 레코드에 붙는 캐시 시간이며, 단위는 초입니다. 예를 들어 `edge.example.net`의 A 레코드 TTL이 60초라면, 리졸버는 조회 결과를 받은 뒤 60초 동안 그 주소를 재사용할 수 있습니다. 위의 CNAME과 A·AAAA 레코드는 각각 자신의 TTL에 따라 캐시됩니다.

TTL이 지난 뒤 같은 이름을 조회할 때는 저장된 결과를 그대로 재사용하지 않고 다시 확인합니다. [Cloudflare TTL 문서](https://developers.cloudflare.com/dns/manage-dns-records/reference/ttl/)

## TCP·QUIC와 HTTP 버전

DNS로 접속할 IP 주소를 얻으면 브라우저는 그 주소의 서버와 연결을 준비합니다. HTTPS로 HTTP/1.1이나 HTTP/2를 사용할 때는 일반적으로 TCP 연결을 맺고, TLS 협상을 거쳐 HTTP 데이터를 전송합니다.

### TCP 핸드셰이크가 필요한 이유

**TCP**(Transmission Control Protocol)는 유실된 데이터를 재전송하고 바이트 순서를 맞추는 전송 프로토콜입니다. 이를 위해 양쪽은 데이터에 순서 번호를 붙이고, 상대가 어디까지 받았는지 확인합니다. 새 연결을 시작할 때도 각자 어느 순서 번호에서 출발할지 알리고, 상대가 그 번호를 받았는지 확인해야 합니다. 이 준비 과정이 **핸드셰이크**(handshake)입니다.

TCP의 기본 연결 수립 과정은 SYN, SYN-ACK, ACK를 주고받는 **3-way handshake**입니다.

1. 브라우저가 **SYN**을 보내 연결을 요청하고 자신의 초기 순서 번호를 알립니다.
2. 서버는 **SYN-ACK**으로 브라우저의 번호를 확인했다고 알리면서 자신의 초기 순서 번호도 보냅니다.
3. 브라우저가 **ACK**으로 서버의 번호를 확인했다고 알립니다. 서버가 이를 받으면 양쪽의 초기 순서 번호를 확인한 상태로 연결이 수립됩니다.

마지막 ACK가 있어야 서버도 자신이 보낸 연결 응답을 브라우저가 받았는지 확인할 수 있습니다. [MDN TCP 핸드셰이크](https://developer.mozilla.org/en-US/docs/Glossary/TCP_handshake), [RFC 9293 연결 수립](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.5)

TCP 연결만으로는 접속한 서버가 `my.example.com`의 서버인지 확인하거나 전송 데이터를 암호화할 수 없습니다. HTTPS에서는 TCP 연결 뒤에 **TLS 핸드셰이크**를 진행해 서버의 신원을 검증하고 암호화에 사용할 알고리즘과 키를 정합니다.

### HTTP/1.1·2와 HTTP/3의 연결 방식

HTTP/3는 TCP 대신 UDP 위의 **QUIC**을 사용합니다. UDP 자체에는 TCP 같은 연결 수립과 재전송 기능이 없지만, QUIC이 연결·스트림·유실 복구 기능을 제공하고 TLS 1.3의 핸드셰이크도 통합합니다. 따라서 HTTP/3에서는 TCP 핸드셰이크 뒤에 TLS를 별도로 진행하는 대신, QUIC 연결 수립 과정에서 보안 협상을 함께 수행합니다.

| 버전     | HTTPS에서 사용하는 기반  | 여러 요청을 처리하는 방식                          |
| -------- | ------------------------ | -------------------------------------------------- |
| HTTP/1.1 | TCP + TLS                | 연결 재사용, 브라우저는 보통 여러 연결로 병렬 요청 |
| HTTP/2   | TCP + TLS                | 한 연결의 여러 스트림으로 요청·응답 다중화         |
| HTTP/3   | QUIC + UDP, TLS 1.3 통합 | 독립적인 QUIC 스트림으로 요청·응답 전달            |

브라우저와 서버는 서로 지원하는 버전으로 통신합니다. 연결을 유지하면 같은 서버에 다음 자원을 요청할 때 DNS 조회와 연결·TLS 협상을 처음부터 반복하지 않아도 됩니다. [MDN HTTP의 발전](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Evolution_of_HTTP), [RFC 9114 HTTP/3](https://datatracker.ietf.org/doc/html/rfc9114)

> **HTTP/3에서는 무엇이 좋아졌나요?**
>
> HTTP/2는 하나의 연결에서 여러 요청을 동시에 처리하지만, 그 요청들이 하나의 TCP 연결을 공유합니다. 예를 들어 CSS와 JavaScript를 받는 중 패킷이 유실되면, TCP가 순서를 맞추기 위해 재전송을 기다리는 동안 두 응답의 전달이 함께 지연될 수 있습니다. HTTP/3의 QUIC은 스트림별로 데이터를 전달하므로, 한 스트림의 유실 때문에 다른 스트림까지 재전송을 기다리는 문제를 줄입니다. 이를 전송 계층의 **HOL 블로킹**(Head-of-Line Blocking) 개선이라고 합니다. [RFC 9114 HTTP/3](https://www.rfc-editor.org/rfc/rfc9114.html#section-1.2)
>
> 연결을 시작할 때도 HTTP/1.1·2의 HTTPS처럼 TCP 연결을 먼저 맺고 TLS를 진행하는 대신, QUIC 연결과 TLS 협상을 함께 수행해 연결 준비에 필요한 왕복을 줄일 수 있습니다. [RFC 9001 QUIC과 TLS](https://www.rfc-editor.org/rfc/rfc9001.html#section-3)

## TLS 핸드셰이크와 인증서 검증

IP 주소에 연결했다고 해서 상대가 정말 `my.example.com`의 서버라는 보장은 없습니다. 가짜 서버와도 암호화된 연결을 만들 수 있기 때문에, 데이터를 암호화하는 것과 올바른 상대에게 보내는 것을 함께 해결해야 합니다. **TLS**(Transport Layer Security)는 서버의 신원을 확인하고, 주고받는 데이터를 암호화해 도청과 변조를 방어합니다. HTTPS는 이 TLS로 HTTP 통신을 보호합니다.

### 서버가 인증서를 보내는 이유

처음 만난 사람이 이름을 말하는 것만으로는 신원을 확인하기 어렵습니다. 그래서 믿을 수 있는 기관이 발급한 신분증을 확인합니다. 서버가 보내는 **서버 인증서**도 비슷한 역할을 합니다. 서버 스스로 “나는 `my.example.com`이다”라고 주장하는 대신, 인증 기관이 확인하고 서명한 문서를 브라우저에 제시하는 것입니다. 이 예시에서는 브라우저와 직접 연결되는 CDN이 인증서를 보냅니다.

인증서가 발급되는 과정부터 보면, 서버 운영자는 먼저 **공개 키와 개인 키**를 준비합니다. 두 키는 수학적으로 연결된 한 쌍으로, 개인 키로 만든 전자서명을 공개 키로 검증할 수 있습니다. 공개 키는 인증서에 넣어 다른 사람에게 보여주고, 개인 키는 서버 측에서 비밀로 보관합니다.

운영자가 `my.example.com`의 인증서 발급을 신청하면, **인증 기관**(Certificate Authority, CA)은 신청자가 해당 도메인을 제어할 수 있는지 확인합니다. 예를 들어 CA가 지정한 값을 DNS 레코드에 등록하게 하고, 그 값이 실제로 조회되는지 검사할 수 있습니다. 확인이 끝나면 CA는 호스트 이름과 서버의 공개 키, 유효 기간 등을 담은 인증서에 자신의 개인 키로 전자서명을 합니다. 이 서명은 인증서의 내용이 해당 CA가 발급한 그대로인지 확인하는 근거가 됩니다. [Let's Encrypt의 인증서 발급 과정](https://letsencrypt.org/how-it-works/)

브라우저가 접속할 때는 서버가 이렇게 발급받아 둔 인증서를 제시합니다. 브라우저는 인증서의 **SAN**(Subject Alternative Name)에 `my.example.com`이 포함되어 있는지 확인하고, 발급자의 공개 키로 인증서의 서명을 검증합니다. 누군가 인증서의 이름이나 공개 키를 바꾸면 기존 서명과 맞지 않아 검증에 실패합니다.

> **신분증에 비유하면**
>
> 인증서의 호스트 이름은 신분증의 이름, CA의 전자서명은 발급 기관이 진위를 확인할 수 있도록 남긴 표시와 비슷합니다. 브라우저는 이름만 읽는 것이 아니라, 믿을 수 있는 기관이 발급했으며 내용도 바뀌지 않았는지 검증합니다. 도메인을 제어하는지 확인하는 일은 발급 시 CA가 수행하고, 접속할 때 인증서를 검증하는 일은 브라우저가 수행합니다.

### 인증서 체인과 브라우저의 검증

신분증을 확인하려면 그 발급 기관을 믿을 수 있어야 하듯, 브라우저도 인증서를 보낸 서버의 말만으로 CA를 신뢰하지 않습니다. 운영체제나 브라우저는 미리 신뢰하는 CA의 인증서와 공개 키를 **신뢰 저장소**에 가지고 있습니다. 이때 신뢰의 출발점이 되는 CA를 **루트 CA**라고 부릅니다.

루트 CA가 모든 서버 인증서를 직접 발급하는 대신, 다른 CA가 인증서를 발급할 수 있도록 그 CA의 인증서에 서명할 수 있습니다. 이 **중간 CA**가 다시 `my.example.com`의 서버 인증서에 서명하면, 루트 CA → 중간 CA → 서버로 이어지는 **인증서 체인**이 만들어집니다. 브라우저는 이미 신뢰하는 루트 CA의 공개 키로 중간 CA 인증서의 서명을 확인하고, 검증된 중간 CA의 공개 키로 서버 인증서의 서명을 확인할 수 있습니다. 처음 보는 서버 인증서를 미리 신뢰하는 CA까지 연결해서 검증하는 방식입니다. [RFC 5280 인증서 경로와 신뢰](https://www.rfc-editor.org/rfc/rfc5280.html#section-3.2)

서버는 TLS 핸드셰이크에서 자신의 인증서와 필요한 중간 CA 인증서들을 보냅니다. 브라우저는 이미 신뢰하는 루트 CA를 자신의 신뢰 저장소에서 확인합니다. [RFC 8446 Certificate 메시지](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.2)

<InfraTlsCertificate />

브라우저는 받은 인증서들과 자신의 신뢰 저장소를 이용해 다음을 확인합니다.

1. **호스트 이름 확인**: 서버 인증서의 SAN이 접속하려는 `my.example.com`과 일치하는지 확인합니다. 신뢰하는 CA가 발급했어도 다른 호스트용 인증서라면 사용할 수 없습니다.
2. **체인의 서명 검증**: 서버 인증서에 서명한 중간 CA를 확인하고, 그 위의 발급자를 따라가며 신뢰하는 루트 CA까지 연결되는지 검증합니다.
3. **유효성 확인**: 체인에 포함된 인증서의 유효 기간과 용도 등의 조건이 맞는지 검사합니다. [RFC 9525 서비스 신원 검증](https://www.rfc-editor.org/rfc/rfc9525.html), [RFC 5280 인증서 경로 검증](https://www.rfc-editor.org/rfc/rfc5280.html#section-6)

### 인증서를 복사한 서버는 어떻게 구별할까요?

인증서가 진짜인지 확인하는 것과, 지금 그 인증서를 제시한 서버가 정당한 상대인지 확인하는 것은 별개의 과정입니다. 신분증도 다른 사람의 것을 복사해서 보여줄 수 있듯이, 인증서 자체는 공개된 정보여서 누구나 복사할 수 있습니다. 그래서 브라우저는 상대 서버가 **인증서의 공개 키와 짝인 개인 키를 실제로 보유하는지**도 확인합니다.

TLS 1.3에서는 서버가 지금까지 주고받은 핸드셰이크 내용을 자신의 개인 키로 서명한 `CertificateVerify` 메시지를 보냅니다. 브라우저는 검증한 인증서의 공개 키로 이 서명을 확인합니다. 인증서만 복사한 가짜 서버는 해당 개인 키가 없으므로 현재 핸드셰이크에 맞는 서명을 만들 수 없습니다. 이 과정을 통해 서버는 개인 키를 보내지 않고도 자신이 그 키를 보유하고 있음을 증명합니다. [RFC 8446 CertificateVerify](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.3)

### TLS 1.3 핸드셰이크에서 주고받는 정보

서버의 신원을 검증하는 동안 브라우저와 서버는 **키 교환**으로 통신을 보호할 키도 만듭니다. 인증서의 공개 키로 HTTP 데이터를 직접 암호화하는 것이 아니라, 키 교환으로 도출한 대칭 키로 데이터를 보호합니다. 인증서 기반 TLS 1.3 연결에서 이 과정은 다음 순서로 진행됩니다.

1. 클라이언트가 `ClientHello`로 지원 버전·암호 알고리즘·키 교환 정보를 보냅니다.
2. 서버가 `ServerHello`로 사용할 조건과 키 교환 정보를 선택합니다. 양쪽은 이를 바탕으로 핸드셰이크 보호에 필요한 키를 도출합니다.
3. 서버가 인증서와 서명, `Finished` 메시지 등을 보냅니다. 클라이언트는 서버 신원과 지금까지의 협상 내용을 검증합니다.
4. 클라이언트도 `Finished`로 협상 내용을 확인하고, 양쪽은 애플리케이션 트래픽 키로 HTTP 데이터를 보호합니다.

<InfraTlsHandshake />

TLS 1.3에서는 `ServerHello` 이후 인증서 등의 핸드셰이크 메시지도 암호화됩니다. [RFC 8446 TLS 1.3](https://www.rfc-editor.org/rfc/rfc8446.html)

### SNI와 ALPN의 역할

하나의 IP가 여러 호스트를 제공한다면 서버는 어떤 인증서를 보여줄지 알아야 합니다. **SNI**(Server Name Indication)는 TLS 협상에 접속하려는 서버 이름을 담는 확장입니다. 브라우저가 보내는 서버 이름을 보고 CDN은 `my.example.com`에 맞는 인증서를 제시할 수 있습니다.

**ALPN**(Application-Layer Protocol Negotiation)은 TLS 연결에서 사용할 애플리케이션 프로토콜을 협상합니다. 예를 들어 HTTP/2의 `h2`와 HTTP/1.1의 `http/1.1` 중 양쪽이 지원하는 값을 선택합니다. [RFC 6066 SNI](https://www.rfc-editor.org/rfc/rfc6066.html#section-3), [RFC 7301 ALPN](https://www.rfc-editor.org/rfc/rfc7301.html)

### CDN에서 TLS가 종료되는 지점

CDN이 WAF 검사와 캐시 조회를 하려면 HTTP 요청을 읽어야 하므로 브라우저와의 TLS 연결은 CDN에서 종료됩니다. CDN이 원본 응답을 가져오는 서버를 **오리진**(origin)이라고 하며, 오리진에 요청할 때는 별도의 연결을 사용합니다. 아래 구성은 두 구간을 모두 TLS로 보호합니다.

## HTTP 요청과 응답

통신 연결을 준비한 뒤에는 **HTTP**로 요청할 작업과 결과를 주고받습니다. 요청의 메서드와 경로는 무엇을 할지, 헤더는 원하는 응답 형식 같은 조건을 전달합니다. 상품 페이지를 여는 요청을 HTTP/1.1 형식으로 쓰면 다음과 같습니다.

```http
GET /products/42 HTTP/1.1
Host: my.example.com
Accept: text/html
```

`GET`은 자원 조회를 요청하고, `Host`는 이 연결에서 어느 호스트의 자원을 원하는지 알립니다. HTTP/2·3에서는 전송 형식이 달라지지만 메서드·경로·상태 코드의 의미는 유지됩니다.

서버는 요청을 처리한 결과를 상태 코드와 헤더, 본문에 담아 응답합니다. 상품 페이지를 정상적으로 만들었다면 `200 OK`와 함께 HTML을 보내고, `Content-Type: text/html`로 본문 형식을 알립니다. CDN과 브라우저는 `Cache-Control` 같은 응답 헤더를 읽어 이 응답을 저장하거나 재사용할 수 있는지 판단합니다. [MDN HTTP 메시지](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Messages)

## CDN에서 요청 검사와 캐시 조회

> **CDN 엣지란?**
>
> CDN이 사용자와 가까운 네트워크에서 요청을 받도록 여러 지역에 배치한 서버입니다. 사용자와 오리진 사이의 긴 왕복 시간과, 같은 콘텐츠를 반복해서 전달하는 오리진의 부담을 줄이기 위해 둡니다. 상품 앱이 실행되는 오리진 앞에서 브라우저의 요청을 받고, HTML·이미지 같은 응답의 복사본을 캐시에 저장해 전달합니다. [CloudFront의 엣지 서버와 오리진](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/HowCloudFrontWorks.html)

### WAF에서 요청 검사

이 구성에서는 CDN에 연결된 **WAF**(Web Application Firewall)가 HTTP 요청의 경로·헤더·본문에 규칙을 적용해 알려진 공격 패턴 등을 검사합니다. 차단된 요청은 여기서 끝나고, 허용된 요청이 캐시 조회로 넘어갑니다. [AWS WAF와 CloudFront 요청 흐름](https://aws.amazon.com/blogs/security/how-to-prevent-hotlinking-by-using-aws-waf-amazon-cloudfront-and-referer-checking/)

### HIT와 MISS에 따라 갈리는 경로

엣지 서버는 요청한 상품 페이지의 응답이 캐시에 있고, 재사용할 수 있는지 확인합니다. 재사용할 수 있으면 오리진에 요청을 전달하지 않고 저장된 HTML을 브라우저에 반환합니다. 이런 캐시 **HIT**에서는 상품 SSR과 API 조회를 생략할 수 있습니다.

재사용할 응답이 없는 **MISS**에서는 엣지 서버가 오리진에 요청을 전달합니다. 상품 SSR 앱이 API 데이터를 조회해 HTML을 만들면 엣지 서버는 이 응답을 받아 브라우저로 전달하고, 캐시 정책이 허용하면 저장해 다음 요청에 재사용합니다. 저장 여부와 재사용 기간은 서버의 `Cache-Control` 응답 헤더와 CDN 설정에 따릅니다. [MDN HTTP 캐싱](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)

## 로드 밸런서와 HTTP 라우터

캐시 MISS로 오리진에 도착한 요청은 **로드 밸런서**(load balancer)를 거칩니다. 로드 밸런서는 여러 대상 중 정상적으로 요청을 처리할 수 있는 곳에 트래픽을 분산합니다. 이 예시에서는 로드 밸런서가 연결을 분산하고, 뒤쪽 HTTP 라우터가 요청을 읽어 상품 앱을 선택합니다.

**L4** 로드 밸런싱은 TCP 같은 연결을 다루며, **L7** 로드 밸런싱은 HTTP 호스트·경로·헤더를 읽어 요청을 구분할 수 있습니다. 따라서 구성에 따라 로드 밸런서가 HTTP 라우팅까지 맡기도 합니다. [AWS 로드 밸런서 FAQ](https://aws.amazon.com/elasticloadbalancing/faqs/)

### 호스트와 경로로 앱 선택

HTTP 라우터는 `my.example.com`으로 들어온 요청의 경로를 보고 앱을 고릅니다. `/products/42`는 상품 SSR 앱에, `/account/profile`은 계정 앱에, `/auth/callback`은 로그인 앱에 전달하는 식입니다. 클라이언트의 요청을 받아 뒤쪽 서버에 전달하는 이런 서버를 **리버스 프록시**라고 부릅니다.

### Kubernetes에서 앱으로 연결

앱은 VM이나 컨테이너 서비스, 서버리스 환경 등에서 실행할 수 있습니다. 이 글에서는 상품 SSR 앱을 **Kubernetes**에서 실행하고, HTTP 라우터가 클러스터 안의 앱으로 요청을 전달하는 구성을 사용합니다.

Kubernetes에서는 **Ingress**나 **Gateway API**로 HTTP 라우팅 규칙을 표현합니다. 실제 요청은 이 규칙을 읽는 Ingress Controller 등의 프록시 구현체가 처리합니다. 라우터가 상품 앱을 선택하면, 다음으로 그 앱의 요청을 처리할 Pod에 연결해야 합니다. [Kubernetes Ingress](https://kubernetes.io/docs/concepts/services-networking/ingress/), [Gateway API 리소스](https://gateway-api.sigs.k8s.io/docs/concepts/api-overview/)

## Service에서 앱 Pod까지

**Pod**는 하나 이상의 컨테이너가 네트워크 등을 공유하는 Kubernetes의 실행 단위입니다. 상품 SSR 앱도 Pod 안에서 실행됩니다. Pod가 교체되면 IP가 바뀔 수 있으므로, **Service**가 대상 Pod를 묶어 안정적인 이름과 접근 지점을 제공합니다.

## HTML을 받은 브라우저의 화면 표시

브라우저는 도착한 HTML을 파싱하면서 문서 구조를 만들고, JS·CSS·이미지를 발견하는 대로 요청합니다. HTML 전체를 받기 전에도 추가 자원을 다운로드할 수 있습니다. 같은 CDN에서 받는 자원은 기존 연결을 재사용할 수 있고, 엣지의 캐시에 있으면 오리진까지 요청하지 않고 받을 수 있습니다.

브라우저는 HTML의 구조와 CSS 규칙을 바탕으로 요소에 적용할 스타일을 계산하고, 각 요소의 위치와 크기를 정한 뒤 화면에 그립니다. [MDN 브라우저의 파싱과 렌더링](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/How_browsers_work#render)

React 같은 프레임워크로 만든 SSR 페이지에서는 **하이드레이션**(hydration)으로 서버 HTML에 상태와 이벤트 처리를 연결합니다. HTML이 먼저 표시된 뒤 JavaScript가 실행되어 버튼 등의 상호작용이 가능해질 수 있습니다.
