목록 안의 삭제 버튼을 클릭했는데 상세 화면까지 열리는 경우가 있습니다. 버튼의 삭제 핸들러에 이어 부모 항목의 클릭 핸들러도 실행되기 때문입니다.

브라우저는 버튼에서 발생한 클릭 이벤트를 부모에게도 전달합니다. React에서도 부모의 핸들러가 실행되지만, 내부에서 핸들러를 찾고 호출하는 방식은 다릅니다. 이 글에서는 브라우저의 이벤트 전파를 먼저 살펴본 뒤, React의 구현 코드에서 부모 핸들러가 실행되는 이유와 전파를 멈추는 방법을 확인해 보겠습니다.

## 버튼을 클릭했는데 부모의 핸들러가 실행되는 이유

다음 코드에는 버튼과 부모 요소에 각각 클릭 리스너가 등록되어 있습니다.

```html
<div id="parent">
  <button id="child">삭제</button>
</div>

<script>
  const parent = document.querySelector('#parent');
  const child = document.querySelector('#child');

  parent.addEventListener('click', () => {
    console.log('부모 클릭');
  });

  child.addEventListener('click', () => {
    console.log('버튼 클릭');
  });
</script>
```

버튼을 클릭하면 `버튼 클릭`, `부모 클릭` 순서로 출력됩니다. 브라우저가 클릭 이벤트를 부모에게 전달하면서 부모에 등록한 리스너도 실행하기 때문입니다.

일반적인 DOM 트리에서 클릭 이벤트의 처리 순서는 다음과 같습니다.

```text
캡처링: window → document → html → body → 부모
타깃:   버튼
버블링: 부모 → body → html → document → window
```

> **캡처링**(capturing)은 조상에서 타깃을 향해 내려가며 이벤트를 처리하는 단계입니다. **버블링**(bubbling)은 타깃에서 조상 방향으로 올라가며 처리하는 단계입니다.

`addEventListener()`의 `capture` 기본값은 `false`입니다. 앞의 코드에서 부모 리스너는 버블링 단계에 실행되므로 버튼의 리스너보다 나중에 호출됩니다. 부모에서 먼저 이벤트를 처리하려면 `{ capture: true }`를 지정합니다.

```js
parent.addEventListener('click', () => {
  console.log('부모 캡처');
}, { capture: true });
```

앞의 예제에 이 코드를 추가하면 실행 순서가 다음과 같이 바뀝니다.

```text
부모 캡처
버튼 클릭
부모 클릭
```

클릭한 버튼 자체에서는 캡처 리스너와 비캡처 리스너가 모두 `AT_TARGET` 단계에 실행됩니다. 이때도 캡처 리스너가 먼저 실행됩니다.

여기까지는 `click`을 기준으로 살펴봤습니다. 다른 이벤트는 버블링하지 않을 수도 있으며, 조상으로 올라가는지는 이벤트의 `bubbles` 값에 따라 달라집니다. [DOM Standard의 이벤트 전파 설명](https://dom.spec.whatwg.org/#introduction-to-dom-events)과 [디스패치 알고리즘](https://dom.spec.whatwg.org/#concept-event-dispatch)에서 이 순서를 확인할 수 있습니다.

## 부모에서 자식의 이벤트 처리하기

이처럼 클릭이 부모에게 전달되므로, 목록의 버튼마다 리스너를 등록할 필요 없이 목록에서 클릭을 받을 수도 있습니다. 다음 코드는 `ul`에 리스너 하나를 등록하고, 클릭한 버튼의 `data-id`를 읽습니다.

```html
<ul id="list">
  <li><button data-id="1">첫 번째 항목</button></li>
  <li><button data-id="2">두 번째 항목</button></li>
</ul>

<script>
  const list = document.querySelector('#list');

  list.addEventListener('click', (event) => {
    const button = event.target.closest('button[data-id]');
    if (!button || !list.contains(button)) return;

    console.log('선택한 항목:', button.dataset.id);
  });
</script>
```

리스너는 `ul`에 등록했지만, `event.target`을 통해 클릭이 발생한 요소를 찾습니다. 이후 목록에 버튼을 추가해도 그 클릭은 같은 `ul`로 전달되므로 기존 리스너에서 처리할 수 있습니다.

> **이벤트 위임**(event delegation)은 자식에서 발생한 이벤트를 조상의 리스너에서 처리하는 방식입니다.

DOM 이벤트 모델에서도 이벤트가 발생한 요소에서 직접 처리하거나, 상위 요소에서 모아 처리할 수 있다고 설명합니다. [W3C DOM Level 2 Events: 이벤트 흐름](https://www.w3.org/TR/2000/REC-DOM-Level-2-Events-20001113/events.html#Events-flow)

### 삭제 버튼의 클릭이 부모에게 전달되는 것을 막기

처음에 언급한 삭제 버튼 예제로 돌아가 보겠습니다. 목록 항목에는 상세 화면을 여는 리스너가 있고, 안쪽 버튼에는 삭제 리스너가 있습니다.

```html
<div id="item">
  주문 내역
  <button id="delete-button">삭제</button>
</div>

<script>
  const item = document.querySelector('#item');
  const deleteButton = document.querySelector('#delete-button');

  item.addEventListener('click', () => {
    console.log('상세 화면 열기');
  });

  deleteButton.addEventListener('click', () => {
    console.log('항목 삭제');
  });
</script>
```

삭제 버튼을 클릭하면 삭제와 상세 화면 열기가 모두 실행됩니다. 삭제 버튼에서 처리한 클릭이 부모 항목으로 올라가기 때문입니다. 삭제 리스너에서 `stopPropagation()`을 호출하면 이후 전파를 중단할 수 있습니다.

```js
deleteButton.addEventListener('click', (event) => {
  event.stopPropagation();
  console.log('항목 삭제');
});
```

`stopPropagation()`은 이처럼 이벤트를 더 전달하지 않으려는 경우에 사용하는 메서드입니다. 2000년 11월 DOM Level 2 Events 권고안에 포함되었으며, 캡처링과 버블링 도중 전파를 중단하는 동작을 정의합니다. [W3C DOM Level 2 Events](https://www.w3.org/TR/2000/REC-DOM-Level-2-Events-20001113/events.html#Events-flow-bubbling)

`stopPropagation()`은 호출한 뒤의 전파를 막습니다. 부모의 캡처 리스너는 자식보다 먼저 실행되므로, 자식에서 전파를 중단해도 이미 실행된 결과는 달라지지 않습니다. 링크 이동 같은 기본 동작을 취소하려면 `preventDefault()`를 사용해야 합니다.

| DOM API | 역할 |
| --- | --- |
| `stopPropagation()` | 이후 경로로의 전파를 중단합니다. |
| `stopImmediatePropagation()` | 전파와 현재 타깃의 나머지 리스너 실행을 중단합니다. |
| `preventDefault()` | 취소 가능한 기본 동작을 취소합니다. `passive: true`인 리스너에서는 취소할 수 없습니다. |

각 메서드의 동작은 DOM 표준에 정의되어 있습니다. [DOM Standard: Event 인터페이스](https://dom.spec.whatwg.org/#interface-event)

## React는 이벤트를 어디에 등록할까

버튼과 부모에 각각 핸들러를 등록하는 코드를 React로 옮기면 다음과 같습니다.

```jsx
function Example() {
  return (
    <div onClick={() => console.log('부모 클릭')}>
      <button onClick={() => console.log('버튼 클릭')}>
        삭제
      </button>
    </div>
  );
}
```

버튼을 클릭하면 `버튼 클릭`, `부모 클릭` 순서로 출력됩니다. 캡처 단계에서 처리하려면 `onClickCapture`를 사용합니다. [React 공식 문서의 이벤트 전파 예제](https://react.dev/learn/responding-to-events#event-propagation)에서도 같은 동작을 확인할 수 있습니다.

출력 결과는 앞의 DOM 예제와 같지만, 리스너가 등록된 위치는 다릅니다. DOM 예제에서는 `button`과 `div`에 각각 `addEventListener()`를 호출했습니다. React는 두 요소 어디에도 `click` 리스너를 등록하지 않습니다. 대신 앞에서 본 이벤트 위임처럼 루트 컨테이너 한 곳에서 클릭을 받고, 호출할 핸들러는 직접 찾아냅니다. 그래서 부모의 `onClick`이 실행되는 이유도 브라우저의 버블링이 아니라 React가 목록을 만드는 방식에 있습니다.

먼저 그 리스너가 언제, 어디에 등록되는지부터 확인해 보겠습니다.

> 아래 코드는 React DOM **v19.2.0** 기준입니다. 하이드레이션이 완료된 화면의 일반적인 `click` 처리를 살펴봅니다. 하이드레이션 도중 이벤트를 보류하거나 다시 처리하는 경우와 다른 이벤트 플러그인의 동작은 다루지 않습니다. 읽는 데 필요하지 않은 타입 선언이나 분기는 생략하고 코드에 표시했습니다.

### 등록 시점은 렌더링이 아니라 루트를 만들 때입니다

리스너 등록은 컴포넌트를 렌더링할 때가 아니라 `createRoot()`가 루트를 만들 때 한 번 일어납니다. `createRoot()`는 컨테이너를 루트로 표시한 뒤 마지막에 `listenToAllSupportedEvents()`를 호출합니다.

[원문 코드: ReactDOMRoot.js의 createRoot, 255–256행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom/src/client/ReactDOMRoot.js#L255-L256)

```js
// createRoot 내부 발췌
markContainerAsRoot(root.current, container);
// 주석 노드를 컨테이너로 쓰는 경우의 처리 생략
listenToAllSupportedEvents(rootContainerElement);
```

이름 그대로 React가 지원하는 이벤트 전부를 이 시점에 등록합니다.

[원문 코드: DOMPluginEventSystem.js의 listenToAllSupportedEvents, 432–459행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/DOMPluginEventSystem.js#L432-L459)

```js
export function listenToAllSupportedEvents(rootContainerElement) {
  if (!rootContainerElement[listeningMarker]) {
    rootContainerElement[listeningMarker] = true;
    allNativeEvents.forEach(domEventName => {
      // selectionchange는 버블링하지 않아 document에 따로 등록합니다.
      if (domEventName !== 'selectionchange') {
        if (!nonDelegatedEvents.has(domEventName)) {
          listenToNativeEvent(domEventName, false, rootContainerElement);
        }
        listenToNativeEvent(domEventName, true, rootContainerElement);
      }
    });
    // selectionchange를 ownerDocument에 등록하는 코드 생략
  }
}
```

`allNativeEvents`는 이벤트 플러그인들이 `registerEvents()`로 모아 둔 네이티브 이벤트 이름의 집합입니다. 반복문은 이 집합 전체를 루트에 등록하므로, 화면에 `onClick`을 쓴 컴포넌트가 하나도 없어도 `click` 리스너는 등록됩니다. 어떤 핸들러를 호출할지는 이벤트가 실제로 들어온 뒤에 계산합니다. 바깥의 `listeningMarker` 검사는 같은 컨테이너에 두 번 등록하지 않기 위한 표시입니다.

반복문 안에서는 `listenToNativeEvent()`를 최대 두 번 호출합니다. 두 번째 인자가 캡처 여부인데, `true` 호출에는 조건이 없고 `false` 호출에만 `nonDelegatedEvents` 검사가 붙어 있습니다. 이 비대칭이 이 함수에서 읽어야 할 부분입니다.

`nonDelegatedEvents`는 DOM에서 버블링하지 않는 이벤트의 목록입니다.

[원문 코드: DOMPluginEventSystem.js의 nonDelegatedEvents, 236–250행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/DOMPluginEventSystem.js#L236-L250)

```js
export const nonDelegatedEvents = new Set([
  'beforetoggle',
  'cancel',
  'close',
  'invalid',
  'load',
  'scroll',
  'scrollend',
  'toggle',
  ...mediaEventTypes,
]);
```

이 이벤트들은 타깃에서 위로 올라오지 않으므로 루트에 버블 리스너를 걸어도 받을 수 없습니다. 그래서 루트 등록을 건너뛰고, 해당 요소를 렌더링하는 시점에 `listenToNonDelegatedEvent()`로 그 요소에 직접 등록합니다. 반면 캡처 단계는 `window`에서 타깃으로 내려가는 경로라 버블링 여부와 관계없이 루트를 지나갑니다. 캡처 등록에 조건이 없는 이유입니다.

`click`은 이 목록에 없으므로 루트에 버블 리스너와 캡처 리스너가 모두 등록됩니다.

### 등록되는 것은 결국 addEventListener입니다

`listenToNativeEvent()`는 캡처 여부를 `eventSystemFlags`에 담아 `addTrappedEventListener()`로 넘깁니다. 실제 등록은 이 함수에서 일어납니다.

[원문 코드: DOMPluginEventSystem.js의 addTrappedEventListener, 460–552행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/DOMPluginEventSystem.js#L460-L552)

```js
// addTrappedEventListener 내부 발췌
let listener = createEventListenerWrapperWithPriority(
  targetContainer,
  domEventName,
  eventSystemFlags,
);
// passive 옵션과 레거시 분기 생략
if (isCapturePhaseListener) {
  unsubscribeListener = addEventCaptureListener(
    targetContainer,
    domEventName,
    listener,
  );
} else {
  unsubscribeListener = addEventBubbleListener(
    targetContainer,
    domEventName,
    listener,
  );
}
```

`addEventCaptureListener()`와 `addEventBubbleListener()`는 `capture`를 각각 `true`와 `false`로 지정해 `addEventListener()`를 호출할 뿐입니다. 앞에서 본 DOM API 그대로입니다.

[원문 코드: EventListener.js의 addEventCaptureListener](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/EventListener.js#L19-L26)

```js
export function addEventCaptureListener(target, eventType, listener) {
  target.addEventListener(eventType, listener, true);
  return listener;
}
```

등록되는 함수는 우리가 JSX에 쓴 핸들러가 아니라 `createEventListenerWrapperWithPriority()`가 만든 래퍼입니다. 이 함수는 이벤트의 우선순위에 따라 래퍼를 고른 뒤, `domEventName`과 `eventSystemFlags`, `targetContainer`를 미리 바인딩해 돌려줍니다.

[원문 코드: ReactDOMEventListener.js의 createEventListenerWrapperWithPriority, 94–119행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/ReactDOMEventListener.js#L94-L119)

```js
const eventPriority = getEventPriority(domEventName);
let listenerWrapper;
switch (eventPriority) {
  case DiscreteEventPriority:
    listenerWrapper = dispatchDiscreteEvent;
    break;
  // ContinuousEventPriority와 기본값 분기 생략
}
return listenerWrapper.bind(
  null,
  domEventName,
  eventSystemFlags,
  targetContainer,
);
```

`click`은 `DiscreteEventPriority`이므로 `dispatchDiscreteEvent`가 선택됩니다. 이 래퍼는 업데이트 우선순위를 설정한 뒤 `dispatchEvent()`를 호출합니다. 바인딩해 둔 `eventSystemFlags`에는 캡처 여부(`IS_CAPTURE_PHASE`)가 들어 있습니다. 루트에는 캡처용과 버블용 래퍼가 각각 등록되어 있고, 둘은 이 플래그로 구분됩니다. 나중에 `onClickCapture`를 찾을지 `onClick`을 찾을지도 이 값으로 갈립니다.

### 클릭은 dispatchEvent로 들어옵니다

버튼을 클릭하면 브라우저는 캡처 단계에서 루트의 캡처 래퍼를, 버블 단계에서 루트의 버블 래퍼를 실행합니다. 두 래퍼 모두 `dispatchEvent()`로 이어지고, 이 함수는 이벤트를 지금 처리할 수 있는지부터 확인합니다.

[원문 코드: ReactDOMEventListener.js의 dispatchEvent, 157–178행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/ReactDOMEventListener.js#L157-L178)

```js
// dispatchEvent 내부 발췌. 보류한 이벤트를 다시 처리하는 분기는 생략했습니다.
let blockedOn = findInstanceBlockingEvent(nativeEvent);
if (blockedOn === null) {
  dispatchEventForPluginEventSystem(
    domEventName,
    eventSystemFlags,
    nativeEvent,
    return_targetInst,
    targetContainer,
  );
  clearIfContinuousEvent(domEventName, nativeEvent);
  return;
}
```

`findInstanceBlockingEvent()`는 `nativeEvent`의 타깃에서 가장 가까운 Fiber를 찾아 모듈 변수 `return_targetInst`에 담아 둡니다. 반환값은 찾은 Fiber가 아니라 **이벤트 처리를 막고 있는 대상**입니다. 아직 하이드레이션되지 않은 영역을 클릭하면 그 컨테이너를 반환하고, React는 이벤트를 큐에 넣었다가 나중에 다시 처리합니다. 막는 것이 없으면 `null`을 반환하며, 이 글에서는 이 경로만 따라갑니다.

[원문 코드: ReactDOMEventListener.js의 return_targetInst](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/ReactDOMEventListener.js#L244-L248)

```js
export let return_targetInst = null;
// 아래 함수가 이 변수에 찾은 Fiber를 담습니다.
export function findInstanceBlockingTarget(targetNode) {
  return_targetInst = null;
  let targetInst = getClosestInstanceFromNode(targetNode);
  // 마운트 여부 확인과 보류 판단 생략
}
```

그래서 `dispatchEventForPluginEventSystem()`에 넘기는 `return_targetInst`가 클릭한 요소에 대응하는 Fiber이고, `targetContainer`는 이벤트를 받은 루트 컨테이너입니다. 이 둘은 각각 "어디서부터 핸들러를 찾을지"와 "어느 트리의 이벤트인지"를 정합니다.

### 수집과 실행으로 나뉩니다

`dispatchEventForPluginEventSystem()`이 하는 일의 대부분은 Portal이나 중첩된 루트를 고려해 시작 Fiber를 보정하는 것입니다. 보정이 끝나면 마지막에 다음 코드를 실행합니다.

[원문 코드: DOMPluginEventSystem.js의 dispatchEventForPluginEventSystem, 688–697행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/DOMPluginEventSystem.js#L688-L697)

```js
batchedUpdates(() =>
  dispatchEventsForPlugins(
    domEventName,
    eventSystemFlags,
    nativeEvent,
    ancestorInst,
    targetContainer,
  ),
);
```

`batchedUpdates()`로 감싸므로 한 번의 클릭에서 여러 핸들러가 상태를 변경해도 렌더링은 한 번으로 묶입니다. 그 안의 `dispatchEventsForPlugins()`가 남은 과정의 지도입니다.

[원문 코드: DOMPluginEventSystem.js의 dispatchEventsForPlugins, 325–344행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/DOMPluginEventSystem.js#L325-L344)

```js
function dispatchEventsForPlugins(
  domEventName,
  eventSystemFlags,
  nativeEvent,
  targetInst,
  targetContainer,
) {
  const nativeEventTarget = getEventTarget(nativeEvent);
  const dispatchQueue = [];
  extractEvents(
    dispatchQueue,
    domEventName,
    targetInst,
    nativeEvent,
    nativeEventTarget,
    eventSystemFlags,
    targetContainer,
  );
  processDispatchQueue(dispatchQueue, eventSystemFlags);
}
```

빈 배열 `dispatchQueue`를 만들고, `extractEvents()`가 호출할 핸들러를 모아 이 배열을 채운 뒤, `processDispatchQueue()`가 배열을 순회하며 실행합니다. 즉 **수집과 실행이 분리되어 있습니다.** 부모의 핸들러가 실행되는 것도, 전파를 중단하는 것도 이 배열 위에서 결정됩니다.

## React가 부모의 핸들러를 찾아 실행하는 과정

`extractEvents()`는 등록된 이벤트 플러그인들에 차례로 이벤트를 넘깁니다. 이 중 `click`을 비롯한 대부분의 이벤트를 처리하는 것이 `SimpleEventPlugin`이고, 나머지 플러그인은 브라우저 간 차이를 보정하는 역할을 합니다.

### 찾을 prop 이름과 이벤트 종류를 정합니다

`SimpleEventPlugin.extractEvents()`는 먼저 네이티브 이벤트 이름을 React prop 이름으로 바꾸고, 만들 이벤트 객체의 생성자를 고릅니다.

[원문 코드: SimpleEventPlugin.js의 extractEvents, 56–115행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/plugins/SimpleEventPlugin.js#L56-L115)

```js
// extractEvents 앞부분을 click 경로만 남겨 발췌
const reactName = topLevelEventsToReactNames.get(domEventName);
if (reactName === undefined) {
  return;
}
let SyntheticEventCtor = SyntheticEvent;
let reactEventType = domEventName;
switch (domEventName) {
  case 'click':
    // Firefox는 오른쪽 클릭에도 click 이벤트를 만들어 여기서 걸러냅니다.
    if (nativeEvent.button === 2) {
      return;
    }
  /* falls through */
  case 'mousedown':
  case 'mouseup':
    SyntheticEventCtor = SyntheticMouseEvent;
    break;
}
```

`topLevelEventsToReactNames`는 `click`을 `onClick`으로 바꾸는 대응표입니다. 여기서 얻은 `reactName`이 곧 Fiber에서 찾을 prop 이름이 됩니다. `SyntheticEventCtor`는 뒤에서 만들 이벤트 객체의 생성자이고, `click`에는 `SyntheticMouseEvent`가 쓰입니다.

이름이 정해지면 핸들러를 모읍니다.

[원문 코드: SimpleEventPlugin.js의 핸들러 수집과 큐 등록, 198–229행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/plugins/SimpleEventPlugin.js#L198-L229)

```js
const inCapturePhase = (eventSystemFlags & IS_CAPTURE_PHASE) !== 0;
const accumulateTargetOnly =
  !inCapturePhase &&
  (domEventName === 'scroll' || domEventName === 'scrollend');

const listeners = accumulateSinglePhaseListeners(
  targetInst,
  reactName,
  nativeEvent.type,
  inCapturePhase,
  accumulateTargetOnly,
  nativeEvent,
);
if (listeners.length > 0) {
  const event = new SyntheticEventCtor(
    reactName,
    reactEventType,
    null,
    nativeEvent,
    nativeEventTarget,
  );
  dispatchQueue.push({event, listeners});
}
```

`inCapturePhase`는 루트에 등록할 때 래퍼에 바인딩해 둔 `eventSystemFlags`에서 읽습니다. 루트의 캡처 리스너가 실행됐다면 `true`가 되고, 이 값이 `accumulateSinglePhaseListeners()`로 그대로 전달됩니다. 캡처 핸들러와 버블 핸들러를 한 번에 모으지 않고, 브라우저가 각 단계에서 리스너를 실행할 때마다 그 단계의 핸들러만 모으는 구조입니다. React 17부터 캡처 단계에 실제 브라우저 캡처 리스너를 사용하기 때문에 가능한 방식입니다. [React 17의 캡처 처리 변경](https://legacy.reactjs.org/blog/2020/08/10/react-v17-rc.html#aligning-with-browsers)

`accumulateTargetOnly`는 조상까지 올라가지 않고 타깃에서 멈추라는 뜻으로, `scroll`과 `scrollend`에만 `true`가 됩니다. `click`은 `false`이므로 조상까지 탐색합니다.

핸들러를 하나도 찾지 못하면 `if` 안으로 들어가지 않습니다. 이벤트 객체는 호출할 핸들러가 있을 때만 만듭니다. 원본 코드에도 `Intentionally create event lazily`라는 주석이 붙어 있습니다.

만들어진 객체가 **합성 이벤트**(`SyntheticEvent`)입니다. React 핸들러가 인자로 받는 객체가 이것이고, 브라우저가 만든 원본은 그 안의 `nativeEvent`에 담깁니다. 핸들러 목록과 이 이벤트 객체는 한 쌍으로 묶여 `dispatchQueue`에 들어갑니다.

### Fiber를 따라 부모의 핸들러를 모읍니다

실제 탐색은 `accumulateSinglePhaseListeners()`가 합니다. 이 함수가 받는 `targetInst`는 앞에서 `findInstanceBlockingEvent()`가 담아 둔, 클릭한 요소에 대응하는 **Fiber**입니다. Fiber는 React가 엘리먼트마다 유지하는 내부 노드이고, `return` 필드로 부모 Fiber를 가리킵니다. 이 함수는 DOM의 `parentNode`가 아니라 이 `return` 체인을 따라 올라갑니다.

[원문 코드: DOMPluginEventSystem.js의 accumulateSinglePhaseListeners, 712–832행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/DOMPluginEventSystem.js#L712-L832)

```js
// accumulateSinglePhaseListeners의 일반적인 click 경로를 발췌·편집
const captureName = reactName !== null ? reactName + 'Capture' : null;
const reactEventName = inCapturePhase ? captureName : reactName;
let listeners = [];
let instance = targetFiber;
let lastHostComponent = null;

while (instance !== null) {
  const {stateNode, tag} = instance;
  if (
    (tag === HostComponent ||
      tag === HostHoistable ||
      tag === HostSingleton) &&
    stateNode !== null
  ) {
    lastHostComponent = stateNode;
    // 실험적 이벤트 핸들 처리 생략
    if (reactEventName !== null) {
      const listener = getListener(instance, reactEventName);
      if (listener != null) {
        listeners.push(
          createDispatchListener(instance, listener, lastHostComponent),
        );
      }
    }
  }
  // 다른 이벤트와 실험적 API의 처리 생략
  if (accumulateTargetOnly) {
    break;
  }
  instance = instance.return;
}
return listeners;
```

첫 두 줄에서 찾을 prop 이름을 확정합니다. `reactName`이 `onClick`이면 `captureName`은 문자열을 이어 붙인 `onClickCapture`가 되고, `inCapturePhase`에 따라 둘 중 하나가 `reactEventName`이 됩니다. 캡처와 버블에서 같은 함수를 쓰되 찾는 prop 이름만 달라지는 셈입니다.

반복문은 Fiber 하나마다 세 가지를 확인합니다.

- **DOM 요소에 대응하는 Fiber인가.** Fiber 트리에는 함수 컴포넌트에 해당하는 노드도 섞여 있습니다. 실제 DOM 요소를 `stateNode`로 가지는 것은 `HostComponent`(일반 `<div>`, `<button>`), `HostHoistable`(`<title>`처럼 `head`로 끌어올려지는 요소), `HostSingleton`(`<html>`, `<body>`)뿐이고, 핸들러는 이 세 종류에서만 읽습니다.
- **그 prop에 함수가 들어 있는가.** `getListener()`가 Fiber의 현재 props에서 `onClick` 값을 꺼냅니다. 이 함수에는 `disabled`가 지정된 폼 요소의 마우스 이벤트를 `null`로 돌려보내는 처리도 들어 있습니다. 비활성화된 버튼을 눌러도 `onClick`이 실행되지 않는 이유가 여기에 있습니다.
- **찾았다면 무엇을 함께 저장할 것인가.** `createDispatchListener()`는 `{instance, listener, currentTarget}` 세 값을 묶습니다. 호출할 함수뿐 아니라 어느 Fiber의 핸들러인지(`instance`)와 방금 지나온 DOM 요소(`lastHostComponent`)를 같이 들고 갑니다. 두 값은 각각 전파 중단 판정과 `event.currentTarget` 설정에 쓰입니다.

마지막 줄의 `instance = instance.return`이 부모 Fiber로 올라가는 부분입니다. 그래서 배열에는 버튼의 `onClick`이 먼저, 부모의 `onClick`이 그 뒤에 담깁니다. **수집 순서는 캡처든 버블이든 항상 타깃에서 조상 방향입니다.** 순서를 뒤집는 일은 실행 단계에서 합니다.

`getListener()`가 읽는 것은 DOM 요소에 대응하는 Fiber의 props입니다. 그래서 `<Button onClick={handler} />`처럼 함수 컴포넌트에 넘긴 prop은 이 반복문에서 수집되지 않습니다. `Button` 내부에서 그 prop을 실제 DOM 요소에 연결하거나 직접 호출해야 합니다.

부모를 `return`으로 찾는다는 점은 Portal에서도 드러납니다. Portal의 내용을 DOM의 다른 위치에 렌더링해도 Fiber의 부모 관계는 그대로입니다. 그래서 Portal 내부를 클릭하면 DOM상으로는 조상이 아닌 React 부모의 핸들러까지 실행됩니다. [React: Portal의 이벤트 전파](https://react.dev/reference/react-dom/createPortal#caveats)

### 캡처는 부모부터, 버블은 자식부터 호출합니다

수집이 끝나면 `processDispatchQueue()`가 큐의 각 항목을 `processDispatchQueueItemsInOrder()`로 넘깁니다. 배열에는 자식, 부모 순서로 들어 있으므로 캡처에서는 마지막 항목부터 읽어야 부모가 먼저 실행됩니다. 버블에서는 첫 항목부터 읽으면 자식이 먼저 실행됩니다.

[원문 코드: DOMPluginEventSystem.js의 processDispatchQueueItemsInOrder, 266–311행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/DOMPluginEventSystem.js#L266-L311)

```js
// 타입 선언과 개발 모드 분기를 생략한 실행 루프
let previousInstance;
if (inCapturePhase) {
  for (let i = dispatchListeners.length - 1; i >= 0; i--) {
    const {instance, currentTarget, listener} = dispatchListeners[i];
    if (instance !== previousInstance && event.isPropagationStopped()) {
      return;
    }
    executeDispatch(event, listener, currentTarget);
    previousInstance = instance;
  }
} else {
  for (let i = 0; i < dispatchListeners.length; i++) {
    const {instance, currentTarget, listener} = dispatchListeners[i];
    if (instance !== previousInstance && event.isPropagationStopped()) {
      return;
    }
    executeDispatch(event, listener, currentTarget);
    previousInstance = instance;
  }
}
```

두 반복문의 차이는 읽는 방향뿐입니다. 같은 배열을 뒤에서부터 읽으면 조상에서 타깃으로 내려가는 캡처 순서가 되고, 앞에서부터 읽으면 타깃에서 조상으로 올라가는 버블 순서가 됩니다. DOM의 전파 순서를 React가 배열의 인덱스로 재현하는 부분입니다.

중단 여부를 확인하는 조건에 `instance !== previousInstance`가 붙어 있습니다. 한 Fiber에서 여러 리스너가 수집되는 경우가 있어서, 인스턴스가 바뀌는 지점에서만 중단을 판정합니다. 같은 요소에 속한 리스너들은 중간에 끊기지 않습니다.

실제 호출은 `executeDispatch()`가 합니다.

[원문 코드: DOMPluginEventSystem.js의 executeDispatch, 252–264행](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/DOMPluginEventSystem.js#L252-L264)

```js
// executeDispatch 내부 발췌
event.currentTarget = currentTarget;
try {
  listener(event);
} catch (error) {
  reportGlobalError(error);
}
event.currentTarget = null;
```

합성 이벤트 객체는 목록 전체가 공유하지만, `currentTarget`은 호출 직전에 이번 핸들러의 DOM 요소로 바뀝니다. 부모의 핸들러에서 `event.currentTarget`이 부모 요소를 가리키는 이유입니다. 호출이 끝나면 다시 `null`로 되돌리므로, 이벤트 객체를 밖으로 넘겨 나중에 읽으면 `currentTarget`은 `null`입니다.

`try`/`catch`로 감싸 예외를 `reportGlobalError()`로 보고하는 점도 눈여겨볼 만합니다. 한 핸들러가 예외를 던져도 반복문은 멈추지 않고 다음 핸들러를 실행합니다.

아래 시각화에서 단계를 넘기면 React가 어떤 Fiber를 확인하고, 어떤 핸들러를 목록에 추가하는지 볼 수 있습니다. 캡처와 버블을 바꿔 보면서 목록을 읽는 방향에 따라 호출 순서가 어떻게 달라지는지도 확인해 보세요. 앞의 구현을 설명하기 위한 모형으로, React를 직접 실행한 결과는 아닙니다.

## stopPropagation()은 React의 실행 루프도 중단합니다

부모의 `onClick`은 브라우저가 부모 요소까지 이벤트를 올려 보내서 실행되는 것이 아니라, 루트의 리스너 하나가 배열을 순회하며 호출하는 것입니다. 따라서 부모의 핸들러를 막으려면 브라우저의 전파가 아니라 이 순회를 멈춰야 합니다. 합성 이벤트의 `stopPropagation()`이 하는 일이 그것입니다.

버튼의 React 핸들러에서 전파를 중단하는 코드는 다음과 같습니다.

```jsx
<button
  onClick={(event) => {
    event.stopPropagation();
    console.log('항목 삭제');
  }}
>
  삭제
</button>
```

여기서 `event`는 React가 만든 합성 이벤트입니다. 이 객체의 `stopPropagation()` 구현을 보면 네이티브 메서드를 호출한 뒤, React가 확인할 중단 상태도 설정합니다.

[원문 코드: SyntheticEvent.js의 stopPropagation](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/SyntheticEvent.js#L105-L124)

```js
stopPropagation: function () {
  const event = this.nativeEvent;
  if (!event) {
    return;
  }

  if (event.stopPropagation) {
    event.stopPropagation();
  } else if (typeof event.cancelBubble !== 'unknown') {
    // 원본의 레거시 브라우저 관련 설명 주석 생략
    event.cancelBubble = true;
  }

  this.isPropagationStopped = functionThatReturnsTrue;
},
```

`this.nativeEvent`는 브라우저에서 받은 원본 이벤트입니다. 이 메서드는 두 가지 일을 합니다. 원본의 `stopPropagation()`을 호출해 루트 바깥으로 올라가는 DOM 전파를 멈추고, 마지막 줄에서 `isPropagationStopped()`가 `true`를 반환하도록 바꿉니다. `functionThatReturnsTrue`는 이름 그대로 `true`만 반환하는 함수입니다.

두 번째가 React 내부를 위한 처리입니다. 앞서 본 실행 루프는 다음 인스턴스의 핸들러를 실행하기 전에 이 값을 확인합니다.

[원문 코드: 핸들러 실행 전 중단 여부 확인](https://github.com/facebook/react/blob/v19.2.0/packages/react-dom-bindings/src/events/DOMPluginEventSystem.js#L291-L297)

```js
if (instance !== previousInstance && event.isPropagationStopped()) {
  return;
}
```

`isPropagationStopped()`가 `true`이면 다음 인스턴스로 넘어가기 전에 `return`하므로 부모의 핸들러를 호출하지 않습니다. 이 확인이 필요한 이유는 배열이 이미 만들어져 있기 때문입니다. 핸들러 목록은 루트 리스너가 실행될 때 한 번에 수집되므로, 브라우저의 전파를 멈춰도 배열에서 부모의 핸들러가 빠지지는 않습니다. 반복문을 멈추는 것은 이 플래그뿐입니다.

그래서 원본 이벤트에 직접 호출하면 결과가 달라집니다.

```js
// React의 반복문과 DOM 전파를 모두 멈춥니다.
event.stopPropagation();

// DOM 전파만 멈춥니다. 부모의 React 핸들러는 그대로 실행됩니다.
event.nativeEvent.stopPropagation();
```

`event.nativeEvent.stopPropagation()`만 호출하면 `isPropagationStopped()`를 바꾸는 줄이 실행되지 않으므로, 반복문은 중단을 알지 못한 채 부모의 핸들러까지 호출합니다. 부모의 React 핸들러를 막으려면 합성 이벤트의 메서드를 호출해야 합니다.

## React 17에서 리스너를 루트로 옮긴 이유

합성 이벤트에서 원본의 `stopPropagation()`까지 호출하더라도, 이벤트가 이미 지나온 경로는 되돌릴 수 없습니다. 이 때문에 React가 이벤트를 어디서 받는지가 중요합니다.

React 16 이하에서는 대부분의 이벤트를 `document`에서 위임받았습니다. React 핸들러가 실행될 때는 네이티브 이벤트가 이미 `document`에 도착한 뒤였습니다.

```text
버튼 → 부모 → React 루트 → document
                           └ React 핸들러 실행
```

이 시점에 `stopPropagation()`을 호출해도 같은 `document`에 등록한 다른 네이티브 리스너는 실행됩니다. React 트리가 중첩된 경우에도 안쪽 트리에서 중단한 이벤트를 바깥쪽 트리가 받는 문제가 있었습니다.

React 17에서는 위임 위치를 각 루트 컨테이너로 변경했습니다.

```text
버튼 → 부모 → React 루트 → document
              └ React 핸들러 실행
                전파를 중단하면 document에 도달하지 않음
```

루트에서 `stopPropagation()`을 호출하면 이벤트가 `document`의 버블 리스너에 도달하기 전에 멈춥니다. 중첩된 React 트리도 양쪽이 React 17 이상이면 안쪽 루트에서 바깥으로 올라가는 전파를 막을 수 있습니다. 앞에서 본 `rootContainerElement`에 리스너를 등록하는 코드는 이때 바뀐 방식입니다. [React 17: 이벤트 위임 변경](https://legacy.reactjs.org/blog/2020/08/10/react-v17-rc.html#changes-to-event-delegation)

`document`의 캡처 리스너는 여전히 루트보다 먼저 실행됩니다. 루트의 React 핸들러에서 전파를 중단해도 이미 실행된 캡처 리스너의 결과는 남습니다.

## 마치며

처음의 삭제 버튼 예제에서 부모 핸들러가 실행된 이유는 React가 버튼에 이어 부모의 핸들러도 목록에 담았기 때문입니다. 버튼의 `onClick`에서 `event.stopPropagation()`을 호출하면 React는 다음 부모 핸들러를 실행하지 않고, 브라우저도 이후 전파를 멈춥니다.

그런데도 부모에서 어떤 처리가 실행된다면, 그 핸들러가 캡처 단계에 등록되어 있는지 확인해야 합니다. 캡처 핸들러는 버튼의 `onClick`보다 먼저 실행되므로 버튼에서 전파를 중단해도 이미 실행된 처리는 남습니다.
